19.10.2026 выяснилось, почему страница `/app/rpd` «не работает» у методистов, но
отвечает у всех, кто проверяет снаружи. `curl -v` с рабочего ноутбука показал
сертификат:

```
subject: CN=77-110-123-227.nip.io
issuer:  O=21-SCHOOL.RU; CN=Certificate Authority
```

Настоящий сертификат сервера — `C=US, O=Let's Encrypt, CN=YE2`. Значит соединение
сотрудника терминируется на корпоративном прокси, который расшифровывает TLS и
пересобирает его своим центром сертификации. Мы и они ходят к серверу разными
путями, поэтому «у меня работает» ничего не доказывает.

Как выглядит обрыв со стороны сервера (расширенный формат журнала, добавлен в тот
же день): запросы приходят и успешно обслуживаются, но браузер их не получает и
повторяет на новом соединении.

```
conn=279476:5  GET /app/rpd 200 4392 rt=0.018 ust=200
conn=279477:2  GET /app/rpd 200 4392 rt=0.013 ust=200
conn=279486:1  GET /app/rpd 200 4392 rt=0.016 ust=200
conn=279488:1  GET /app/rpd 200 4392 rt=0.019 ust=200
```

Четыре подряд, каждый за 13–19 мс, последние два — на свежих соединениях. В
браузере при этом `ERR_EMPTY_RESPONSE`. В `error.log` пусто, 5xx нет, контейнер без
рестартов.

**Почему:** `ERR_EMPTY_RESPONSE` означает, что соединение закрылось, не отдав ни
байта. Раз сервер ответ записал, а клиент ничего не увидел, обрыв происходит на
промежуточном узле — на том самом прокси. Смена соединения на каждую попытку —
почерк браузера, которому ответ обрезали.

**Как применять:** при жалобе «страница не работает» сперва попросить с того же
рабочего места `curl -sv <адрес> -o /dev/null` и посмотреть строку `issuer`. Чужой
центр сертификации означает прокси в середине, и дальше искать надо не в коде.
Решающий артефакт — в Chrome DevTools на неудачном запросе «Copy as cURL»: его
можно повторить и сравнить. Проверки с нашей стороны (сервер, домашняя сеть) этот
путь не воспроизводят.

Поставленный 19.10 опыт: для `/app/rpd` добавлен отдельный блок nginx с
`gzip off` — такие прокси чаще всего спотыкаются на сжатом ответе с chunked.
Опыт **не подтверждён**: в репозиторий не переносился, живёт только в
`/etc/nginx/conf.d/cf.conf`. Откат — копия `cf.conf.bak-gzip-20261019`, формат
журнала до правки — `cf.conf.bak-20261019`; после любой правки
`nginx -t && systemctl reload nginx`. Если опыт подтвердится, блок надо перенести
в `deploy/nginx-cf.conf`, иначе он пропадёт при следующей выкладке.
