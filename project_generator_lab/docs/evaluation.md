# Проверка готового проекта и дашборд

Первый контур проверки по документу «Критерии подготовленного контента» от
02.11.2026. Оценивается выдаваемый комплект вместе с согласованными требованиями,
контекстом УП, заданиями и P2P-чек-листом. Проверка не согласует проект и не
блокирует генерацию, исправления или скачивание.

## Как пользоваться

В чате контента нажать **«Проверка по 56 критериям»**. Откроется отдельная страница.
Можно выполнить проверки кодом либо включить содержательный анализ моделью.
Необязательный перечень файлов описывает только выдаваемые файлы, а не результаты,
которые участник создаст сам. Без такого перечня критерий 40 останется без данных.

Вверху показаны рекомендация, полнота проверки требований, основной процент и
экспертный обзор без баллов и влияния на результат. Ниже — цепочки ОР,
критерии 1–40 и отдельная группа экспертных замечаний 41–56 с фильтрами.
Раскрытие критерия показывает основание, цитаты, предложенную правку и исходную
рубрику. По цитате можно открыть фрагмент именно проверенной версии комплекта.
Отчёт скачивается в Markdown или JSON.

## Архитектура

```text
Готовый контент + разрешённые входы
                 ↓
          Неизменяемый снимок
                 ↓
       Опись и проверки кодом
                 ↓
     Модельные пакеты по критериям
                 ↓
       Проверка цитат и цепочек ОР
                 ↓
      Расчёт рекомендации кодом
                 ↓
        Дашборд и экспорт отчёта
```

- `evaluation/criteria.json`, `registry.py`: все 56 исходных рубрик без изменения
  формулировок; версия профиля и SHA-256 исходного DOCX.
- `evaluation/models.py`: типизированные контракты снимка, свидетельства, оценки,
  цепочки ОР и сохранённого отчёта.
- `evaluation/snapshot.py`: фактические README, чек-лист и материалы из сборщика
  выдаваемого ZIP, тексты заданий и разрешённые исходные требования.
- `bridge.evaluation_context`: полные извлечённые тексты с учётом исключений и
  политики УП; сокращённая писательская выдержка не подменяет источник.
- `evaluation/engine.py`: опись, применимость, модельные пакеты и проверка цитат.
- `evaluation/policy.py`: формула, покрытие и приоритет критических замечаний.
- `evaluation/api.py`, `store.py`: задачи, восстановление, права владельца, экспорт.
- `static/evaluation.*`: отдельная страница результатов.

Состояния задачи: `running → complete / partial / interrupted`.
Для каждого критерия отдельно хранятся `assessed`, `not_applicable`, `no_data`,
`unverified`, `pending`, `error`. Оценка +1/0/−1 есть только у `assessed`.
Непрочитанный документ, невыполненная проверка и технический сбой различимы.

## Основания и границы оценки

Модель должна вернуть по одному результату для каждого запрошенного критерия.
Каждая принятая оценка содержит точную цитату существующего фрагмента снимка.
Код проверяет ID и дословное совпадение; выдуманная цитата снимает оценку.
Это проверяет существование основания, но не доказывает логическую верность
вывода модели. Смысловое соответствие остаётся предметом калибровки методологами.

Для ОР требуются цитаты фактических действий, результата и P2P в обязательных
заданиях. Ссылка на согласованный план или бонус сама по себе цепочку не подтверждает.

Критерии 21, 33, 42, 49 требуют контрольного выполнения: этот контур его не
имитирует и файлы не запускает. Для времени прохождения, сопоставимости оценок,
нагрузки проверяющего и предметного подтверждения анализ текста не даёт +1
без дополнительного свидетельства. Нужны дальнейшие адаптеры исполнения и апробации.

Код сверяет наличие запланированных материалов и утверждённый перечень, проверяет
распознанные пути. Совпадение имён файлов не доказывает совпадение их утверждённых
содержательных версий: критерий 40 с одним лишь перечнем не получает +1.

## Решение

По оценённым критериям 1–40: `(сумма + n) / (2 × n) × 100`.
Критерии 41–56 с 03.11.2026 — отдельный экспертный обзор: наблюдения, точные
цитаты, предложения улучшения и вопросы методологу. Баллов и суммы нет.
Статус, сбой, отсутствие или отрицательное содержание такого обзора не меняют
процент, полноту, критические замечания и итоговую рекомендацию по 1–40.
Для старых отчётов это применяется при чтении, без переписывания истории.
НП, Н/д, неподтверждённые и невыполненные проверки не входят в знаменатель.
Покрытие всегда показано отдельно: высокий процент при пробелах не означает готовность.

Стартовые пороги документа 85/70 сохранены как экспериментальный профиль.
Критерии 3, 20, 21, 29, 31, 33 могут влиять на готовность независимо от
процента. Для 20 требуется конкретная ошибка в ответе, используемом для оценки
участника; обычное сомнение в факте не превращается в такой блокер.
Все выводы остаются рекомендациями, `blocks_workflow=false`.

## Повторная проверка и воспроизводимость

Отчёт содержит полный снимок, версию и отпечаток критериев, промпта и движка,
ID модели, время, число вызовов и токены. Изменение текста, чек-листа, выдаваемых
материалов, требований, УП или правил делает прежний отчёт устаревшим.

Завершённая проверка неизменного комплекта возвращается без новых вызовов.
После сбоя завершённые оценки с неизменными зависимостями используются повторно.
Зависимости смысловых оценок пока консервативны: весь комплект. Это не обещание
точечного пересчёта любого изменения. Принудительная полная переоценка доступна
через `force=true`; она запускает новые модельные вызовы.

Пакет — до 8 критериев, максимум 7 последовательных вызовов за проход;
одновременно допускаются две задачи. После сбоя провайдера новые пакеты не
запускаются. При перезапуске сервера задача становится `interrupted`, готовые
результаты остаются. Контекст свыше 400 000 знаков не обрезается молча:
содержательная проверка откладывается, ограничение видно в отчёте.

Отчёты находятся в `PROJECT_LAB_CONTENT_DIR/evaluations/<run>/<report>.json`.
Запись атомарная, доступ проверяется по владельцу исходного проекта и отчёта.
Схема хранения 7; это изменение политики не добавляет сохраняемых полей,
миграция БД не нужна. Движок 1.2 и новый профиль исключают повторное использование
прежних числовых оценок экспертного блока при новом запуске.
Повреждённый отчёт не останавливает запуск приложения.

## Проверка реализации

Автоматические проверки используют тестовые ответы, а не настоящую оценку
педагогического качества. Браузерная проверка использует отдельные каталоги и
тестовый адаптер без платных вызовов. До широкого применения нужны проекты с
независимыми оценками методологов: расхождения по критериям, ложные критические
замечания, пропущенные дефекты и полнота свидетельств.
