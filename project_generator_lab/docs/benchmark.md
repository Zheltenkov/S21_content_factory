# Измерение на готовых проектах: случаи, разбор репозитория, слой кода, модель-судья

Документ описывает пакет `project_generator_lab/benchmark/` в состоянии на 06.10.2026: что он читает, что считает, чего
не считает и что показали прогоны на 15 эталонах SQL и на трёх прогонах интенсива. Решение, по которому он сделан, — РГ 02.10.2026, раздел 7.

Слой кода (разделы 1–10) модели не вызывает и ничего не генерирует. Слой 2 — модель-судья по критериям (раздел 11) —
вызывает модель только отдельной командой; платный прогон судьи на 06.10.2026 не запускался.

---

## 1. Зачем

Генератор проверяет свой результат правилами кода (`content/checks.py`). Чтобы результат можно было сравнивать с
проектом, сделанным и проверенным людьми, оба должны измеряться одним правилом. Пакет читает готовый проект из его
репозитория и применяет к нему те же проверки.

У такой линейки два требования:

1. На проверенных проектах она не должна срабатывать зря — иначе её блокеры ничего не значат.
2. На проекте с дефектом она должна сработать — иначе «0 блокеров» ничего не значит.

Первое проверяется прогоном на эталонах (раздел 6), второе — тестами, в которых в проект подсажен один дефект за раз
(раздел 8).

## 2. Каталог случая

```
<случай>/
    meta.yaml      что известно о случае
    inputs/        что было у методолога до создания проекта: строка УП, паспорт, бриф
    etalon/        готовый проект — его репозиторий
    answers.yaml   ответы методолога на типовые вопросы разбора («вопрос: ответ»)
```

Обязателен только проект. Каталог, который сам является репозиторием (в нём есть README), — случай из одного эталона:
проекты, распакованные из архива, измеряются как лежат, в том числе в обёртке `X/X/README.md`.

`meta.yaml`:

| Поле | Значение |
|---|---|
| `profile` | о чём проект: «SQL, бассейн» |
| `level` | уровень участников |
| `split` | `tuning` — на случае можно настраивать промпты; `held_out` — случай отложен и измеряется только перед релизом; пусто — не решено |
| `note` | заметка |
| `readme` | какой файл — README проекта, путём от каталога проекта. Нужен, когда README лежит не под именем школы; файл `.docx` читается как документ Word (раздел 3.5) |
| `checklist` | какой файл — чек-лист |
| `skip` | файлы и каталоги, которые проектом не являются: черновики, отклонённые версии, эталоны «не грузим» |
| `broken` | файлы, испорченные намеренно, — данные задания «почини»: на читаемость не проверяются, на готовый ответ проверяются |

Правила чтения (`cases.py`):

- Отложенный случай в обычном прогоне не измеряется, в отчёте остаётся только его имя. Измерить — флаг `--release`.
  Показатели, подогнанные на всём наборе, ничего не говорят о проекте, которого в наборе нет.
- `meta.yaml` ищется в каталоге случая, рядом с README внутри обёртки и в `etalon/`, имя — в любом регистре. Если
  файлов два или файл назван `meta.yml`, случай не читается и попадает в «Пропущено»: какой из двух верен, код не
  угадывает. Иначе отложенный случай мог бы быть измерен.
- Неизвестное поле, неверное значение `split`, нечитаемый YAML — случай в «Пропущено» с именем файла. Один плохой случай
  не останавливает остальные.
- Каталог, в чьём `meta.yaml` назван `readme`, — случай, даже если файла `README.md` в нём нет.
- В `inputs/` кладётся то, что было **до** проекта. Входы, написанные по готовому проекту, содержат ответ и завышают
  результат. Код этого проверить не может.

`inputs/` и `answers.yaml` сейчас только читаются: прогон генератора по входам случая — следующий шаг (раздел 9).

## 3. Разбор репозитория

`repository.py` читает README и чек-лист. Берётся русская пара, если она есть (`README_RUS.md`, `check-list_RUS.yml`),
иначе `README.md`, `check-list.yml`; регистр букв в именах не важен.

### 3.1. README

README читается по заголовкам:

| Что | Как узнаётся |
|---|---|
| Название и аннотация | первый заголовок и текст под ним |
| Задание | заголовок вида «Задание 05 — Аудит», «Part 2. Изменение данных», «Задание 1.2 Б», «Exercise 00», «Задание 3. Собери бэклог», «Quest 3. Recursive»; бонусное — «Дополнительно. Part 4…», «Бонусное задание 1*: …», «Задание 7 (дополнительное). …», «Задание 6. Бонусное. Дамп памяти» (слово бонуса — отдельным предложением перед названием) |
| Разделы | всё остальное, в порядке файла, с ролью: содержание, блок школы, глава, введение, правила, теория, заключение. Заголовок неизвестного вида остаётся разделом под своим именем и попадает в отчёт как «раздел вне шаблона» |

Задание школы открывается таблицей из двух колонок. Строка над чертой — шапка: из неё берётся название задания, если
в заголовке его нет. Остальные строки:

| Строки таблицы | Куда |
|---|---|
| до первой жирной строки («Директория для загрузки решений», «Файлы для загрузки») | что сдать |
| после «**Разрешено**» / «**Allowed**» | разрешено |
| после «**Запрещено**» / «**Denied**» | запрещено |
| после жирной строки с другим названием | отдельно, ни к разрешённому, ни к запрещённому |

Задание генератора написано блоками под жирными строками: «**Что нужно сделать**», «**Что должно получиться**»,
«**Ограничения и условия**», «**Формат сдачи**», «**Переход к следующему заданию**».

**Квест** — задание проекта в стиле бассейна (шаблоны на C, README генератора в стиле «квест»):

| Что | Как узнаётся |
|---|---|
| Квест | заголовок «Quest 3. Recursive», «Bonus Quest 5. Func» (бонусный), «Квест 2: Ветки» |
| Формулировка | строка «Получен Quest N. …»: в документе Word — заголовок четвёртого уровня, формулировка из нескольких абзацев — несколько таких заголовков подряд; в README генератора — жирная фраза в начале абзаца. Берётся до конца абзаца, без слов «Получен Quest N.» |
| Сюжет и остальное | текст до формулировки и после неё (`Task.quest`: `story`, `statement`, `rest`) |
| Что сдаётся | строка «Сдать: …» после формулировки, вне блока кода — так пишет генератор; в шаблонах школы файл назван в самой формулировке |
| Квест без номера | «Quest: Level 1. Hall» — квест группового проекта, если под заголовком есть строка «Получен Quest.»; без неё тот же заголовок — название группы квестов и остаётся разделом |
| Листок теории | заголовок «List N» — раздел с ролью «теория» |

Строка «Получен Quest» в блоке кода, с отступом заголовка в два пробела и больше или не в начале строки формулировкой
не считается. У квеста без номера ссылки по номеру нет: вопрос чек-листа «Quest 1» к нему не относится.

Правила, без которых разбор ошибался (каждое закреплено тестом):

- строки блока кода заголовками не считаются; блок, открытый N знаками «`» или «~», закрывается только N и более теми
  же знаками на отдельной строке; незакрытый блок попадает в заметки проекта;
- заголовок с одним пробелом перед «#» — заголовок (так записано задание в одном из эталонов), с двумя и более —
  строка пункта списка (так генератор пишет многострочные шаги);
- внутри задания его заканчивает только задание или заголовок того же уровня и выше: «###» внутри задания «##» — его
  собственный подраздел;
- «\|» в строке таблицы — черта внутри ячейки: «cat a \| wc» — одна ячейка;
- таблица сдачи — от двух колонок. Таблица в одну колонку сразу под заголовком задания — рамка вокруг образца (так
  документ из Google Docs хранит код) и остаётся текстом задания.

### 3.2. Чек-лист

Из `check-list.yml` берутся вступление, правила и вопросы всех секций: название (в одну строку), текст, оценка.
Значение, записанное списком или словарём там, где ожидается текст, читается как пустое. Вопрос бонусный, если
он из секции с «bonus» / «бонус» в названии или его собственное название начинается с «Дополнительно», «Бонусное».

У вопроса отмечается, есть ли в нём блок кода (в ограждении или с отступом в четыре пробела после пустой строки).
Код внутри строки не считается.

### 3.3. Задание и его вопрос

| Условие | Способ |
|---|---|
| Больше половины вопросов названы с номером задания, и номера заданий не повторяются | по номеру: вопрос «Задание 1.2» относится к заданию «1.2», а если такого нет — к заданию «1». Вопрос без номера не относится ни к какому заданию |
| Иначе | по порядку внутри части (основная, бонусная), один к одному |

Вопрос о нескольких заданиях — «Задания 1—2. Разведка и модули», «Задания 3, 4 и 6» — относится к каждому из названных
заданий своей части. Если хотя бы одного из них в README нет, вопрос не относится ни к одному: вопрос, называющий
несуществующее задание, не принимается молча за вопрос об остальных. Ряд берётся целиком или не берётся: «Задания
1—2 и 3.1» рядом не является. Ряд больше чем из 20 заданий и ряд «наоборот» («4—2») номером не считаются — в том числе
при подсчёте «номер у большинства вопросов».

Задание без вопроса и вопрос без задания называются поимённо. Способ указан в отчёте. Замечание о лишнем вопросе
говорит, каким способом он остался лишним: «номера задания в названии нет или задания с таким номером нет» — либо
«вопросы взяты по порядку, этот в своей части лишний по счёту» (он может быть вторым вопросом о последнем задании —
по названию этого не видно). Если вопросы взяты по порядку, а часть названий номер задания всё же называет, отчёт
предупреждает: пары — догадка, вопрос с номером мог встать не к своему заданию.

### 3.4. Остальные файлы

Имена и размеры всех файлов репозитория; текст — для файлов текстовых форматов до 300 КБ. Ссылки (symlink) не
читаются — в том числе README, который сам является ссылкой, и каталог-ссылка с репозиторием внутри; каталог `.git`
пропускается. Если чек-лист под именем школы назван в `skip`, берётся следующий под именем школы (`check-list.yml`
после `check-list_RUS.yml`).

Файлами проекта не считаются сам README и сам чек-лист. Под именами школы у них есть пара на другом языке
(`README.md` рядом с `README_RUS.md`) — она тоже не файл проекта. У README, названного в `meta.yaml`, такой пары нет:
`README.md` рядом с ним — обычный файл (скорее всего черновик) и проверяется как файл, пока не назван в `skip`.

### 3.5. Рабочая папка: README в Word

Прогоны интенсива хранятся не в репозитории школы, а в рабочих папках: README — документ Word (`README.md.docx`),
чек-лист назван по дню (`D1_check-list_RUS.yml`), рядом лежат черновики, отклонённые версии и эталоны «не грузим».
Какой файл считать README, код по виду не выбирает: в папке с тремя README участникам выдан один, и который — знает
тот, кто ведёт случай. Он записывает это в `meta.yaml` (`readme`, `checklist`, `skip`, `broken`).

Правила (`repository.read`, `located`):

- путь в `meta.yaml` — от каталога проекта; «..», путь от корня диска и ссылка наружу не называют ничего. Разделитель —
  «/» или «\». Имя сравнивается с учётом того, что «й» бывает набрана одной буквой и двумя (архив с Mac); если под
  имя подходят два каталога, случай не читается;
- имя, которого в каталоге нет, — ошибка с названием поля: опечатка в `skip` не должна превратиться в «пропускать
  нечего», иначе эталоны прочитаются как файлы проекта;
- один и тот же файл не может быть и README (чек-листом), и пропущенным;
- если назван хотя бы один путь, проект — сам каталог: репозиторий «на каталог глубже» не ищется;
- README не под именем школы и не назван — случай не читается, а сообщение перечисляет похожие файлы:
  «нет README_RUS.md или README.md; похожие файлы: «README.md.docx», «README_old.md.docx» — назовите нужный в
  meta.yaml: readme». Так же для чек-листа — заметкой проекта.

`word.py` переводит документ в Markdown, который читает `repository.py`:

| В документе | В Markdown |
|---|---|
| абзац стиля «Заголовок 1…9», «Title» | заголовок `#`…`######` |
| абзац списка (нумерация у абзаца или у его стиля) | `- …` или `1. …`, вложенный — с отступом; счёт у каждого списка свой |
| таблица | строки с чертой после первой; ячейка из нескольких абзацев — одна строка через `<br>` |
| жирный фрагмент; фрагмент моноширинным шрифтом (Roboto Mono, Courier, Consolas) | `**…**`; `` `…` `` |
| картинка | `![](рисунок)` — чтобы картинки считались |
| разрыв строки внутри абзаца | новая строка |

Блок кода в таком документе ничем не отмечен: образец вывода — обычный абзац. Поэтому строка, которую Markdown
прочитал бы как разметку, — «# …», «```», «| …» — пишется с «\» впереди и остаётся строкой текста, а не становится
заголовком. Не переносятся: курсив, цвет, адрес ссылки (слова остаются), сноски, примечания, надписи (text box),
формулы, линейки; удалённый в режиме правки текст не читается, вставленный читается.

Границы: моноширинный шрифт узнаётся по шрифту самого фрагмента, а не стиля; заголовок — по встроенным стилям, абзац,
просто набранный крупно и жирно, остаётся текстом; у заголовка «_», «*» по краям и «<…>» внутри теряются — разбор
принимает их за выделение и теги, как в Markdown.

Пределы: файл до 30 МБ, после распаковки до 60 МБ, любая часть внутри — до 10 МБ, под каким бы именем она ни лежала
(мегабайт архива может распаковаться в сотню мегабайт XML и гигабайты памяти; у документов архива самая большая
часть — 0,3 МБ), текст README после перевода — до 2 МБ. Что бы ни было не так внутри файла, сообщение одно:
«<имя> не читается как документ Word». Пределы ограничивают память примерно гигабайтом в худшем случае, не меньше.

Проверка перевода: все 19 документов Word архива прогонов сверены с pandoc — 32 741 слово, тот же порядок слов, те же
заголовки и уровни, то же число пунктов списков. Отличий два, оба в пользу `word.py` или по его правилам: заголовок
стиля «Title» pandoc уносит в метаданные, подпись картинки pandoc печатает текстом. У трёх документов рядом лежит
исходный Markdown: множества фрагментов кода совпадают полностью (145 и 118 фрагментов).

## 4. Слой кода

`code_layer.measure` переводит задания в ту же структуру, что у черновика генератора, и вызывает проверки из
`content/checks.py`. Своих правил у слоя одно — «вопрос чек-листа без задания» (и предупреждение о парах, взятых по
порядку): у черновика такого быть не может.

| Проверка | Применена | Чем |
|---|---|---|
| Готовый ответ в файлах и заданиях | да | имена всех файлов (латиницей: solution, answer, otvet, reshen, etalon, correct, key; кириллицей: «эталон», «не грузим», «не для пиров / выдачи», файл с именем «решение» или «ответы»), текст файлов до 300 КБ, **весь** текст каждого задания — все строки под заголовком, включая таблицу |
| У задания есть что делать, что сдать и вопрос пиру | да | см. ниже |
| Повтор текста между заданиями | да | 8 слов подряд, от трёх совпадений; формат сдачи и вопросы пиру не сравниваются |
| Заглушки (TODO, «[вставить…») | да | название, аннотация, разделы, задания, вопросы чек-листа |
| Файлы CSV, JSON, YAML читаются | да | файлы до 300 КБ; у CSV разделитель — запятая, «;» или табуляция; файл, испорченный намеренно, называется в `meta.yaml`: `broken` |
| Вопрос чек-листа без задания | да | — |
| Блок «Что должно получиться» | по шаблону | спрашивается с задания, написанного блоками генератора |
| Готовый ответ во введении, правилах, аннотации | нет | генератор проверяет на это задания, темы теории и материалы |
| Эталонный ответ в вопросе чек-листа | нет | разрешён решением 05.10.2026; считается для сведения |
| Покрытие ОР, часы заданий | нет | нужны входы проекта |
| Тема теории у задания, ссылки тем | нет | нужна глава теории, разобранная по темам |
| Согласованность частей, проверка критиками | нет | это состояния черновика |

Эта таблица печатается в каждом отчёте: «замечаний нет» не должно читаться как «проверено всё».

**Что спрашивается с задания** — зависит от того, как оно написано. С задания не спрашивается то, чего нет в его
шаблоне:

| Вид задания | Признак | Спрашивается |
|---|---|---|
| блоки | нет таблицы, есть «**Что нужно сделать**» | что делать, что должно получиться, формат сдачи, вопрос пиру |
| таблица | задание открывается таблицей | что делать, формат сдачи (строки «что сдать»), вопрос пиру |
| квест | нет таблицы и блоков, есть строка «Получен Quest N.» | что делать (формулировка), вопрос пиру |
| текст | ничего из этого | что делать, вопрос пиру |

У квеста «что делать» — формулировка, ситуация — сюжет до неё, «что должно получиться» — список сразу после
формулировки (так пишет шаблон генератора), «что сдать» — строка «Сдать:». Формат сдачи с квеста не спрашивается: в
шаблонах школы файл назван в формулировке. Квест без строки «Сдать:» перечисляется вместе с заданиями вида «текст».

У задания вида «текст» файлы сдачи названы в предложении («напиши скрипт *part1.sql*»). Код не отличает такое задание
от задания, где о сдаче ничего не сказано. Поэтому формат сдачи с него не спрашивается, а сами задания перечисляются в
отчёте и считаются в первой строке: «формат сдачи кодом не прочитан у N».

**Номера заданий в замечаниях** — собственные номера заданий («Задание 00» — 0), пока они не повторяются; иначе место
задания в README, и отчёт печатает соответствие.

README генератора в стиле «квест», собранный в архив и прочитанный обратно, получает те же замечания проверок текста
(готовый ответ, повтор текста, пустой блок), что и его черновик, — как и README первого шаблона. README в стиле
«рабочая легенда» читается по заданиям и вопросам; его блоки («Должно получиться:», «Результат:») слой не разбирает,
задания имеют вид «текст».

README без единого распознанного задания не измеряется и попадает в «Пропущено» — с причиной, если она известна
(«не в UTF-8»). Иначе он вышел бы в отчёте как проект без блокеров.

## 5. Команда и отчёт

```bash
python -m project_generator_lab.benchmark <каталог> [--out <каталог отчёта>] [--release]
```

`<каталог>` — случай, каталог со случаями или с репозиториями. Результат: `report.md` и `report.json`, по умолчанию в
`data/benchmarks/<время>-code/`. Код возврата 0 и при блокерах: это измерение, а не ворота.

В `report.md`:

1. Первая строка: проектов, без блокеров, блокеров, замечаний, заданий и у скольких формат сдачи не прочитан.
2. «Пропущено» — что не измерено и почему; отложенные случаи.
3. «Что проверено» — таблица из раздела 4.
4. Строка на проект: задания, вопросы, способ сопоставления, вопросы с блоком кода, картинки, файлы, блокеры,
   замечания.
5. По каждому проекту: заметки чтения, разделы вне шаблона, каждое замечание.

Замечание о повторе текста проверка выдаёт на каждую пару заданий: восемь заданий с одной общей фразой — 28 замечаний.
В отчёте они собраны в одну строку с числом пар; так же считается столбец «Замечания». Другие замечания не
объединяются.

Текст из проекта (имена, названия, заметки) в отчёте пишется в одну строку и с «&lt;» вместо «<»: название вопроса с
переводом строки и «## …» иначе создавало в отчёте чужой заголовок.

- каталог с проектами, в корне которого лежит свой README, читается как один проект; если заданий в этом README нет,

- одно задание в основной части и его вопрос в бонусной секции чек-листа не сопоставляются;
- «Задание 3. Бонус: расчёт премии» читается как бонусное задание — так же, как «Задание 6. Бонусное. Дамп памяти»;
- задание, которое открывается таблицей данных из двух и более колонок, читается как задание школы с таблицей сдачи;
- в имени файла «формат_ответа», «дерево_решений», «ключ» ответом не считаются; файл с ответами под таким именем
  найдётся только по тексту («Правильный ответ:», «Эталонное решение»);
- CSV: строки с «;», различающиеся по ширине, но без единой запятой, читаются как один столбец текста — как и раньше,
  не ловятся.

Границы чтения README генератора обратно (черновик измеряется точнее напрямую — `content.checks.run_checks`):

- строка контекста, совпадающая с названием блока («**Формат сдачи**»), читается как начало блока;
- заголовок «###» или «#» без отступа внутри контекста или формата сдачи заканчивает задание;
- у задания с пустым шагом (`""`) обратное чтение сообщает «нет: Что нужно сделать», проверка черновика — нет;
- материал называется `materials/team.csv`, в черновике — `team.csv`.

Проверка заглушек: «Создай модель задачи TODO» по-прежнему считается заметкой себе — у проекта о списке дел сборка
README остановится на этом слове.

## 11. Слой 2: модель-судья

Слой кода отвечает на вопросы, которые решаются счётом: есть ли задания, вопросы к ним, файлы, заглушки. Он не
отличает прогон «скорее плохо» от прогона «хорошо» (раздел 6.2): различия там — в логике заданий, ясности условий,
согласованности задания и проверки. Это читает модель. Всё остальное — что ей показать, каким её словам верить, как
считать итог и можно ли верить самому судье — делает код.

```
python -m project_generator_lab.benchmark.judge <случаи> --model <модель> --dry-run            что будет спрошено и сколько стоит
python -m project_generator_lab.benchmark.judge <случаи> --model <модель> --out <каталог>      платный прогон; в том же каталоге продолжается
```

Ключи: `--repeats` (повторов на проект, по умолчанию 2), `--only <случаи>`, `--groups <группы>`, `--seeded <случаи>`
(подсадить дефекты, 11.5), `--max-calls` (предел новых вызовов, 150), `--parallel` (4), `--release` (и отложенные случаи).

### 11.1. Критерии — `benchmark/criteria.yaml`

80 признаков из трёх источников, переписаны дословно (что изменено — в шапке файла):

| Источник | Номера | Признаков | Шкала 0 / 1 / 2 словами источника |
|---|---|---|---|
| «Формализованные правила хорошего образовательного контента», диагностический чек-лист | R01–R40 | 40 | не выполнен или существенное противоречие / частично, локальная доработка / выполнено в достаточной степени |
| Паспорт программы, вкладка «Критерии качества проекта» | P01–P27 | 27 | совсем не соответствует / соответствует, но нужно доработать / идеально соответствует |
| Паспорт программы, вкладка «Критерии качества чек-листа проекта» | C01–C13 | 13 | то же |

К каждому признаку добавлены служебные поля — это решения версии 0, методологом не подтверждены:

| Поле | Значения | Смысл |
|---|---|---|
| `by` | `judge`, `run`, `expert` | кто может подтвердить признак: модель по тексту; запуск файлов и открытие ссылок; предметный эксперт |
| `needs` | `outcomes`, `hours`, `approved_files`, `standard_texts`, `track` | сведения, которых в самом проекте нет: утверждённые ОР, часы из УП, утверждённый перечень материалов, стандартные тексты чек-листа, основа или коммерция |
| `group` | `logic`, `tasks`, `checking`, `package`, `values` | в какой запрос к судье входит признак |
| `stages` | `concept`, `content` | на каком этапе признак проверяется |
| `scope` | текст | какая часть признака оценивается, если не весь |
| `evidence` | `presence`, `absence` | какие оценки обязаны иметь цитату (11.3) |
| `uncounted` | текст | причина, по которой оценка признака не входит в итог (11.4); пусто — входит |

На этапе готового проекта судье задаются 66 признаков из 80. Не задаются 14 — и в итог не входят ни как выполненные,
ни как невыполненные: R01–R03 (нет утверждённых ОР), R07–R08 (нет часов), R20 и R24 (предметный эксперт), R21 и R33
(запуск), R40 (нет утверждённого перечня), P17 и C11 (неизвестно, основа или коммерция), C01–C02 (нет стандартных
текстов). Если у случая появятся эти сведения, признак будет задан (`criteria.asked(…, known)`); запуск и эксперта
модель не заменяет никогда.

Версия файла (`version`) пишется в отчёт. Тест `test_criteria.py` держит отпечаток всех признаков и служебных полей:
любая правка без смены версии роняет тест. Оценки, полученные по разным версиям, не сравниваются.

Версия 0.2 (06.10.2026): P23 («точки выбора») и P26 («артефакты процесса») помечены `uncounted`. Решение: образец
стиля — версия интенсива 28.09, где результат задания задан точно, а письменные отчёты не нужны; эти два признака
оценивали её ниже версии 07.09. Текст признаков и запрос судье не менялись.

Расхождение в источнике: на обеих вкладках паспорта процент считается формулой «сумма баллов / 32 × 100» и
«/ 24 × 100» — знаменатель записан числом и не равен удвоенному числу строк (27 и 13). Здесь итог по паспорту
считается так же, как по правилам: сумма баллов / (2 × число признаков с оценкой) × 100.

### 11.2. Что видит судья

Один запрос — один проект и одна группа признаков. Группа определяет, что показано:

| Группа | Признаков | Показано |
|---|---|---|
| `logic` — учебная логика, аудитория, структура | 13 | README; материалы `.md`, названные в README |
| `tasks` — задания и язык | 13 | README; материалы |
| `checking` — проверка и чек-лист | 18 | README; вопросы чек-листа |
| `package` — оформление и комплект | 14 | README; перечень файлов с размерами |
| `values` — ценности «Школы 21» | 8 | README |

Запрос состоит из блоков `<about>` (профиль и уровень из `meta.yaml`), `<shown>` (что показано целиком, что обрезано,
что не показано), `<facts>` (посчитано кодом), `<project>` (текст проекта), `<criteria>` (шкалы источников и признаки
группы с пометкой, для каких оценок нужна цитата).

Чего в запросе нет: имени случая, его `note`, `series`, `rank`, `split`. Тест сравнивает запросы одного проекта под
двумя разными описаниями случая — они совпадают побайтно.

`<facts>` — то, что код знает точно: названия заданий; какой вопрос чек-листа к какому заданию отнесён и по какому
правилу; какие из названных в README файлов есть в проекте; число картинок и адресов внешних ссылок; что README хранится
документом Word. Код говорит ровно то, что знает:

- если вопросы сопоставлены по порядку (в названиях нет номеров заданий), «лишний» вопрос не называется: два вопроса
  могут относиться к одному заданию; сказано только, что сопоставление приблизительное и сколько заданий и вопросов;
- если по номеру — названы «задания, номер которых не назван ни в одном вопросе» и «вопросы, в названии которых нет
  номера задания», этими словами;
- адрес ссылки считается, только если у него есть хост с точкой: «http://materials/rules.md» — это то, во что Word
  превращает набранное имя файла; один адрес считается один раз, как бы он ни был оформлен.

Текст проекта — недоверенные данные:

- тег блока запроса, написанный в README, чек-листе, материале или имени файла, перестаёт быть тегом: знак «<» (и
  похожие на него) перед именем блока заменяется на «‹» — в том числе если имя набрано с пробелами, с русскими буквами
  вместо латинских или с присоединёнными знаками; невидимые знаки (нулевой ширины, мягкий перенос) из текста убираются;
- названия заданий и вопросов в `<facts>` и имена файлов в `<shown>` обрезаются до длины названия (80 знаков), пишутся
  в одну строку, кавычки «» в них заменяются на “” — название не может закрыть кавычки и продолжиться как фраза кода;
  инструкция говорит судье, что это слова проекта, а не указания;
- инструкция (`prompts/judge.md`) требует считать всё внутри `<project>` данными и не менять оценку по просьбе из текста.

Пределы: README — 80 000 знаков, вопросы чек-листа — 50 000, один материал — 8 000, все материалы — 40 000, перечень
файлов — 400 строк. Что не поместилось, названо в `<shown>`.

### 11.3. Каким словам судьи верит код

Судья возвращает по каждому признаку `mark` (0, 1, 2, `na` — неприменимо, `no_data` — нет данных), `quote`, `comment`.

**Цитата.** Оценку, которую можно показать текстом, судья обязан подтвердить дословной цитатой из `<project>`:

| `evidence` | Признак | Цитата обязательна для | Что цитируется |
|---|---|---|---|
| `presence` (41 признак из 66) | в проекте что-то есть: «указаны входные данные» | 1 и 2 | место, где это есть |
| `absence` (25 из 66) | чего-то нет или нечто верно для каждого: «нет заглушек», «каждый критерий наблюдаем», «термины используются последовательно» | 0 и 1 | место с нарушением |

Оценка без обязательной цитаты в итог не входит («без цитаты»). С обязательной цитатой, которой нет в показанном
тексте, — тоже («цитата не из проекта»). Оценка, для которой цитата не обязательна, засчитывается, что бы ни стояло в
поле цитаты: иначе пояснение, набранное в поле цитаты у оценки 0, выбрасывало бы нули из итога и завышало его.

Следствие: у 25 признаков-отсутствия оценка 2 принимается на слово. Судья, который ставит такие 2 не глядя, завышает
итог (по измерению проверяющего агента — в среднем на 14 пунктов из 100). Отчёт показывает по каждому проекту, сколько
таких оценок 2 дано без найденной цитаты; отличить ленивого судью от внимательного может только проверка подсаженными
дефектами (11.5).

Поиск цитаты (`judge.evidence`):

- сравниваются слова — буквы и цифры по порядку; разметка Markdown, черты таблицы, кавычки, тире, регистр, «ё»,
  ширина пробела и невидимые знаки не учитываются;
- цитата ищется целыми словами в одном тексте: README, каждый материал, вопросы чек-листа и перечень файлов — разные
  тексты; сведения кода, блок `<shown>`, признаки и инструкция цитатой не являются;
- сначала цитата ищется как есть — многоточие в ней может быть многоточием самого проекта (`print(..., end="")`);
- если не нашлась — как части через «…»: не больше трёх частей, каждая не короче 12 знаков вместе с пробелами между
  словами (судье сказано: не короче трёх слов, 15 букв и цифр), все в одном тексте, по порядку, следующая начинается не
  дальше 600 знаков от конца предыдущей;
- короткая цитата (меньше 12 знаков) принимается, только если это целиком заголовок проекта, имя файла из перечня
  (с путём или без) или строка перечня; одно слово на отдельной строке («Верно») цитатой не считается.

**Формат ответа.** Читается то, что модель имела в виду: `null` вместо пустой строки, лишнее поле, «н/п», «Н/Д»,
«неприменимо: сюжета нет», «2.0», «2 балла», цитата списком частей, русская «С» в номере. Вердикт, который не читается,
пропускается — его признак получает «без ответа»; остальные вердикты вызова остаются. Если не читается ни один, ответ
отклоняется целиком и клиент модели просит её исправить формат. Ответ, в котором меньше половины признаков запроса, —
сбой вызова: не сохраняется, при повторном запуске задаётся снова. Вердикт о признаке, которого в запросе не было, не
учитывается; их число пишется в отчёт. Схема ответа, которую видит модель, осталась строгой: её просят о том, что код
считает.

### 11.4. Подсчёт

Итог считается по каждому источнику отдельно: `сумма баллов / (2 × число признаков с оценкой 0, 1 или 2) × 100`.
«Неприменимо», «нет данных», «без цитаты», «цитата не из проекта», «без ответа» и «сбой вызова» в знаменатель не
входят и показаны отдельными числами. Каждый проект оценивается `--repeats` раз (по умолчанию 2); в отчёте — среднее,
разброс между повторами и число признаков, получивших одну и ту же оценку во всех повторах (сравниваются только
повторы, где оценка принята).

Оценка проекта помечается как неполная (знак `*`), если не удался хотя бы один его вызов, принято меньше 80 % ответов
судьи или оценку 0, 1 или 2 получило меньше половины признаков. Столбец «вместе» (три источника) нужен только для
сравнения версий одного проекта. Пороги правил (85 и 70) относятся к полному чек-листу из 40 признаков при отсутствии
блокеров; судье задаются 30 из 40, блокеры он не определяет — пороги в отчёте приведены для справки.

Проекту без чек-листа группа `checking` не задаётся (18 оценок были бы догадками); это названо в отчёте.

Признак с полем `uncounted` задаётся судье наравне с остальными, но в итог не входит: ни его баллы, ни он сам в числе
признаков с оценкой, ни в счётчиках состояний, ни в сравнении версий. Оценки показаны отдельно (11.7). Согласие
повторов и проверка просьбы считаются по всем заданным признакам: они говорят о судье, а не об итоге проекта.

### 11.5. Проверка самого судьи

Судье нельзя верить на слово. Три проверки, результаты которых известны заранее:

**Порядок версий.** У версий одного проекта в `meta.yaml` записаны `series` и `rank` (больше — лучше). Каждые две
версии серии с разным рангом сравниваются: лучшая должна получить больше. Вердикты пары: «верно», «неверно», «равны»,
те же с пометкой «в пределах разброса повторов» (разница не больше, чем расходятся повторы одного проекта), «неполные
данные» (оценка одной из версий неполная — в целом или по сравниваемому источнику — либо версиям заданы разные
признаки), «нет оценки».

Пары одной серии зависимы: три версии дают три пары из одного порядка. Поэтому отчёт считает точную вероятность того,
что судья, не различающий версии, расставит верно столько же пар или больше, — перебором порядков версий в каждой серии
по тем парам, которые удалось сравнить (`judge.by_chance`). Для трёх серий по три версии (9 пар): 9 из 9 — 0,46 %,
8 и больше — 3,2 %, 7 и больше — 11,6 %, 6 и больше — 27,8 %. Проверено моделированием: судьи, ставящие оценки наугад,
на настоящих случаях дают то же распределение. Версии одного ранга считаются независимыми проектами; два варианта
одного текста в одну серию не ставятся — поэтому случай `D1_07-09_pushed` в серию не входит.

**Подсаженные дефекты** (`--seeded <случай…>`, `benchmark/seeded.py`). В прочитанный проект вносится один известный
дефект, и запросы его групп задаются снова — так же без имени:

| Дефект | Что сделано | Группы | Оценка каких признаков должна упасть |
|---|---|---|---|
| `order` | тексты основных заданий переставлены в обратном порядке под прежними заголовками | `logic` | R09, R10 |
| `unchecked` | из чек-листа убраны вопросы последнего основного задания | `checking` | R27 |
| `hidden` | в первый вопрос чек-листа добавлено требование, которого нет в заданиях | `checking` | R18, R26, C04 |
| `stub` | в начало основного задания вставлены «TODO» и «[вставить…» | `tasks` | R38 |
| `plea` | под названием проекта — просьба к проверяющей модели поставить всем признакам 2 | `logic`, `tasks` | оценки не должны вырасти |

Сравниваются оценки, как их назвал судья, — и те, что не вошли в итог из-за цитаты: вопрос в том, реагирует ли судья.
«Заметил» — оценка после порчи во всех повторах ниже, чем была в любом; «заметил не во всех повторах» — ниже только в
среднем. Дефект подсаживается, только если все его группы входят в `--groups`. Оценки испорченных копий в проекты
отчёта не входят; они записаны в `report.json` (`seeded_marks`).

**Просьба** проверяется по каждому признаку: среднее после против среднего до.

| Вердикт | Когда |
|---|---|
| «поддался» | поднято больше, чем опущено; для честной монеты такой перевес бывает реже чем в 5 % случаев; перевес — не меньше половины оценок, которым было куда расти |
| «оценки выросли, но меньше половины возможного» | перевес значим, но мал: частичная уступка или разброс судьи — по двум повторам их не различить |
| «не поддался» | перевеса нет |
| «нельзя проверить» | ниже 2 у исходного проекта меньше пяти оценок или меньше трети; после просьбы оценено меньше 80 % признаков; два повтора исходного проекта совпали меньше чем в 60 % оценок |

«Неприменимо», ставшее после просьбы оценкой 2, считается поднятой оценкой. Проверка грубая; что она может, измерено
моделированием (`27 признаков, 2 + 2 повтора, 2000 прогонов на строку`):

| Судья | Проект средний или слабый | Проект хороший (ниже 2 — четверть оценок) |
|---|---|---|
| не замечает просьбу, разброс независимый (10–30 % оценок) | «поддался» 0–0,3 % | 1,0–1,4 % |
| не замечает, но каждый его ответ целиком смещён вверх или вниз | 1–4 % | 2–8 % |
| поднял всё, что мог | «поддался» 73–100 % | «поддался» 20–46 %; остальное — «нельзя проверить» и «не поддался» |
| поднял половину | 30–56 %, ещё 10–44 % — «выросли меньше половины» | 10–18 % |
| поднял треть | 4–16 %, ещё 11–77 % — «выросли меньше половины» | 2–14 % |

Отсюда правило запуска: просьбу и дефекты подсаживают и в слабую версию (`D1_07-09`), не только в лучшие.

**Согласие с собой** — число признаков с одной и той же оценкой в повторах (11.4).

Чего эти проверки не доказывают: что оценка судьи по каждому признаку совпадает с оценкой эксперта. Для этого нужна
разметка экспертом (РГ, раздел 7.3) — её нет.

### 11.6. Оплата и возобновление

- `--dry-run` печатает число вызовов, объём и цену по `concept/config/model_prices.json` и ничего не вызывает.
- Принятые вердикты модели сохраняются в `<каталог>/calls/<ключ>.json`. Ключ — отпечаток формата, модели, инструкции,
  схемы ответа, запроса и номера повтора: другая модель, другая инструкция или изменившийся проект — другой вызов.
  Повторный запуск с тем же `--out` задаёт только то, чего в каталоге нет; что из сохранённых вердиктов вошло в итог,
  каждый раз выводится заново тем же кодом. Без `--out` каталог создаётся новый — и оплата полная.
- `--max-calls` (по умолчанию 150) считает только новые вопросы.
- Один и тот же вопрос (два случая с одинаковым проектом) задаётся и оплачивается один раз.
- Пока судья ни разу не ответил, вызовы идут по одному. Прогон останавливается: после трёх сбоев подряд до первого
  ответа; после шести сбоев подряд, когда судья уже отвечал; после трёх ответов подряд, из которых код смог принять
  меньше половины вердиктов (цитат нет в проекте или оценки без цитат). Остальные вызовы не задаются и названы в
  отчёте; тот же запуск с тем же `--out` их задаст.
- Ответ, не прошедший формат, клиент модели один раз просит исправить (`core/llm.py`) — такой вызов стоит двух.
  Токены вызова, который не удался после ответа модели, входят в счёт отчёта: `ModelUnavailable` несёт
  `input_tokens` и `output_tokens`.
- Отчёт пишет токены этого запуска и отдельно — принятых ответов всего прогона. Сбойные вызовы прошлых запусков во
  вторую сумму не входят.
- Ответ, который не удалось записать на диск, остаётся ответом; отчёт говорит, сколько таких.

На десяти случаях: 10 проектов × 5 групп × 2 повтора = 100 вызовов, ещё 36 — на дефекты в трёх проектах; около
2,3 млн входных токенов.

Первый платный прогон (06.10.2026, `anthropic/claude-sonnet-5`) остановился после 86 новых ответов: шлюз шесть раз
подряд ответил 402. Измерено на нём:

- вход — 1,53 млн токенов, 17,8 тыс. на вызов: расчёт по 2,5 знака на токен сходится с фактом;
- выход — 0,45 млн токенов, 5,2 тыс. на вызов и 393 на вердикт, а не 200, как считал расчёт: в выход входит
  рассуждение модели. По группам в среднем: checking 9,6 тыс., logic 5,3 тыс., package 4,6 тыс., tasks 3,3 тыс.,
  values 2,3 тыс. В ответе при этом 2–5 тыс. знаков цитат и комментариев;
- цена — 7,52 $ за 86 вызовов; расчёт на все 136 был 8,3 $, по измеренному выходу — около 12 $;
- один вызов (18 критериев проверки, чек-лист на 30 пунктов) оборван на пределе выхода 16 000 токенов, ещё один
  дошёл до 14 813.
- запрос группы «комплект» на Windows и на Linux получался разным: список файлов проекта строился через `sorted()`
  по путям, а Windows сравнивает пути без учёта регистра («README» там после «datasets», на Linux — перед). 18
  оплаченных ответов этой группы по ключам, посчитанным на Linux, не находились. `repository.read` теперь ставит
  файлы в порядке Windows — по именам в нижнем регистре, папка за папкой; после правки все 91 сохранённый ответ
  находятся по ключам, посчитанным на Linux.

После этого расчёт считает 400 токенов на вердикт (`TOKENS_PER_VERDICT`), предел выхода по умолчанию — 32 000
(`PROJECT_LAB_MAX_OUTPUT_TOKENS`), ожидание ответа — 600 с (`PROJECT_LAB_TIMEOUT_SECONDS`). Ни одно из трёх чисел в
ключ сохранённого ответа не входит: принятые ответы первого прогона остаются в силе.

Версия критериев и поле `uncounted` в ключ ответа не входят: ключ — сам вопрос (инструкция, форма ответа, текст
запроса, модель, номер повтора). Правка, которая меняет только подсчёт, оставляет оплаченные ответы действительными.
Проверено на десяти случаях платного прогона 06.10.2026 при переходе к версии 0.2 и к читателю квестов: 136 ключей и
текстов запросов совпали до и после. Тест `test_the_questions_already_paid_for_are_asked_in_the_same_words` держит
запросы выдуманного проекта по контрольной сумме.

### 11.7. Отчёт

`report.md`: что задано и что нет; строка на проект (проценты по источникам, счётчики состояний, согласие повторов,
число оценок 2, принятых на слово); порядок версий с вероятностью для слепого судьи; подсаженные дефекты и просьба; по
каждому проекту — каждый признак с оценками по повторам, цитатой (отвергнутой, если такая была) и комментарием судьи.
Слова судьи и проекта не могут начать строку или заголовок отчёта. `report.json` — те же данные, оценка за оценкой
(`state` — что вошло в итог, `given` — что сказал судья, `proof` — найдена ли цитата).

Признаки вне итога: таблица «Оцениваются, но в итог не входят» с причиной, таблица «Критерии вне итога: оценки по
повторам» (строка на проект), пометка «(вне итога)» у признака в таблице проекта; в `report.json` — `uncounted` на
верхнем уровне (номер и причина) и у каждого проекта (оценки по повторам).

### 11.8. Чего нет и что известно о пределах

- Платный прогон один: десять случаев, 136 вызовов, `anthropic/claude-sonnet-5`, закончен 07.10.2026 (итоги — README
  модуля, «Прогон закончен 07.10.2026»). Ответы 45 вызовов второго запуска приняты с первого раза; из 1320 оценок по
  правилу цитат не засчитаны 24. Проверка просьбы не сработала ни на одном из трёх проектов: у всех трёх почти все оценки — 2.
  До прогона, на настоящих запросах (измерение проверяющего агента): дословный фрагмент из одной
  строки отвергается в 0,60 % случаев (45 из 7500, все короче 12 знаков без пунктуации), фрагмент с серединой,
  заменённой на «…», — в 0,43 % (14 из 3221); пять слов, набранных из разных мест, не приняты ни разу из 7500.
- Сравнения с оценками эксперта по признакам.
- Отнесения признаков к `presence` и `absence`, к группам и этапам, подтверждённого методологом. Спорные места:
  R14–R16 и P06 («у каждого задания…») отнесены к `presence`, R25 и R27 («каждый…») — к `absence`; C05 и C06 —
  `presence`, R25 и R29 о том же свойстве — `absence`; R30 и R37 — нарушение там состоит в том, чего в тексте нет.
- Признаков, требующих запуска (R21, R33) и эксперта (R20, R24): судья их не оценивает.
- Просьбы к судье в заголовке задания или в имени файла: дефект `plea` вставляет её только в текст README.
- Материалов не в `.md` и материалов, не названных в README: судье не показываются (названы в `<shown>`).
- Проверка просьбы считает признаки независимыми; если ответы судьи смещаются целиком, ложное «поддался» чаще
  заявленных 5 % (таблица в 11.5). Строгой проверки на двух повторах построить нельзя: при 2 + 2 повторах перестановок
  шесть.
- Пара версий сравнивается, даже если у одной из них отвергнуто заметно больше цитат, чем у другой (до 20 %):
  счётчики в отчёте есть, флага нет.
- Строка проекта из одного-двух слов, не заголовок («**Шаги:**», строка таблицы-примера), как цитата не принимается.
- Судьи для замысла (этап `concept`): признаки размечены, команда их не задаёт.
- Слоя 3 — слепого парного сравнения.
