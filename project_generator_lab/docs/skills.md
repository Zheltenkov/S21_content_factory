## 1. Что это

**Навык** — единица, в которой платформа учитывает, чему научился участник: «Git», «Python», «Problem solving».
За сданный проект участник получает баллы по навыкам этого проекта.

**Справочник навыков** — закрытый список названий, которые знает платформа. Проект можно завести на платформе только
с навыками из справочника. Справочник фиксированный и пополняется отдельно; подготовка проекта новые навыки не
придумывает и не предлагает. В паспорте программы справочник лежит на вкладке «Available skills».

**Развесовка** — таблица, которая отвечает на два вопроса про каждый проект:

1. Какую **долю** занимает каждый навык в проекте. Строка `all`. Доли в сумме дают 1 (100%).
2. Как **баллы каждого навыка делятся между заданиями** проекта. Строки `01`, `02`, … По каждому навыку доли заданий
   в сумме дают 1.

У проекта две части, и считаются они раздельно: **основная** (обязательные задания) и **бонусная**. У бонусной свои
доли навыков (`Bonus all`) и своё деление по бонусным заданиям (`Bonus 01`, …).

**Как из долей получаются баллы:**

```
балл задания по навыку = XP проекта × доля навыка в проекте × доля задания в навыке
```

Пример со встречи РГ 02.10.2026: проект на 80 XP, навык с долей 20% — это 16 баллов навыка; заданию 3 отдано 40% этого
навыка — 6,4 балла.

**Требования платформы** (по решениям РГ 02.10.2026 и письменному ответу 05.10.2026):

- у проекта есть хотя бы один навык, каждый — из справочника;
- доли навыков в проекте в сумме дают 100%;
- по каждому навыку доли заданий в сумме дают 100%;
- основная и бонусная часть — раздельно;
- если сумма не сходится или навыка нет в справочнике, платформа ввод отклоняет.

**Кто и когда это задаёт:**

| Что | Когда | Кто |
|---|---|---|
| Набор навыков проекта | на этапе учебного плана | автор УП; после заведения проекта на платформе набор не меняется |
| Доли навыков в проекте (строка `all`) | не определено: вместе с УП или при разработке проекта | — |
| Доли по заданиям | при разработке проекта: до неё заданий нет | методолог проекта |
| XP проекта | не определено: в шаблоне паспорта XP нет | — |

Отсюда место развесовки в подготовке проекта: **набор навыков — вход**, модель его не подбирает. Суммы и
принадлежность справочнику **считает и проверяет код**, не модель: модель в арифметике ошибается, а платформа ошибку
не прощает.

## 2. Где это лежит в паспорте

Паспорт программы — книга XLSX с вкладками; образец — «Паспорт программы_Батон» (21 вкладка). Для навыков значимы
четыре.

### 2.1. Вкладка «УП»

Строки проектов. Навыков в ней нет, но есть **код проекта** — колонка «Название проекта на платформе и в Gitlab»
(`D1P1_Terminal`). Код — единственное, что связывает строку УП с блоком развесовки.

### 2.2. Вкладка «Available skills» — справочник

| № | Skills | *(без заголовка)* |
|---|---|---|
| 1 | 3D modeling | TRUE |
| 2 | AB-Testing | TRUE |
| 3 | Algorithms | TRUE |
| … | … | … |

94 названия. Колонка без заголовка сразу после «Skills» — признак, доступен ли навык на платформе.

### 2.3. Вкладки развесовки

В «Батоне» их три:

| Вкладка | Что это |
|---|---|
| «Развесовка skills - ВЕРСИЯ со С» | текущая развесовка проектов |
| «Развесовка skills (OLD)» | прежняя версия; заголовки те же |
| «Развесовка_exam skills» | развесовка экзаменов; к проектам не относится |

Раскладка одна: `Проект | Задание | <навык> … <навык> | check`. Колонки навыков общие для всей вкладки (в «Батоне»
12). На каждый проект — блок строк. Настоящий блок из «Батона» (показаны только навыки этого проекта):

| Проект | Задание | Git | Python | Network & system administration | Problem solving | check |
|---|---|---|---|---|---|---|
| D1P1_Terminal | all | 0,2 | 0,3 | 0,3 | 0,2 | 1 |
| | 01 | 0,2 | 0 | 0,15 | 0 | |
| | 02 | 0 | 0,1 | 0,2 | 0,3 | |
| | 03 | 0,65 | 0 | 0 | 0 | |
| | 04 | 0,05 | 0 | 0,4 | 0,2 | |
| | 05 | 0,05 | 0,7 | 0,05 | 0,25 | |
| | 06 | 0,05 | 0,2 | 0,2 | 0,25 | |
| | check | 1 | 1 | 1 | 1 | |
| | Bonus all | 0,1 | 0,5 | 0,1 | 0,3 | 1 |
| | Bonus 01 | 0,5 | 0,4 | 0,5 | 0,35 | |
| | Bonus 02 | 0,5 | 0,6 | 0,5 | 0,65 | |
| | check | 1 | 1 | 1 | 1 | |

Как читать блок:

- строка `all`: проект на 20% про Git, на 30% про Python, на 30% про сети и администрирование, на 20% про решение
  задач. `check` справа — сумма по строке, должна быть 1;
- колонка «Git» вниз: из всех баллов Git задание 01 даёт 20%, задание 03 — 65%, задания 04–06 — по 5%. Строка `check`
  внизу — сумма по колонке, должна быть 1;
- `Bonus all` и `Bonus 01`, `Bonus 02` — то же для бонусной части;
- код проекта стоит только в строке `all`; пустая ячейка — ноль.

## 3. Как модуль читает книгу

Читает и проверяет **код**, модель в этом не участвует.

### 3.1. Путь файла

```
страница: «Загрузить учебный план» (.csv или .xlsx)
   │  POST /api/curriculum  (файл; необязательное поле skills_tab — выбранная вкладка развесовки)
   ▼
concept/runs.py — книга разбирается в отдельном процессе с лимитами памяти и времени (core/isolated.run)
   ▼
ingestion.parse_curriculum
   ├─ read_book ─┬─ plan_tab        — вкладка с проектами: по заголовку «Название проекта»
   │             └─ skill_tabs_of   — справочник и вкладки развесовки: по заголовкам
   ├─ строки проектов (как раньше)
   └─ attach_skills ─┬─ skills.parse_blocks  — вкладка → блоки проектов
                     ├─ skills.strangers     — каких названий нет в справочнике
                     └─ skills.block_issues  — что в блоке не сходится
   ▼
Curriculum (план со справочником, блоками и заметками) → ответ странице
```

CSV — один лист, вкладок в нём нет: развесовка читается только из книги.

### 3.2. Как находятся вкладки

По **заголовку** — первой заполненной строке среди первых 50, — а не по названию вкладки и не по её месту в книге.
Названия у разных программ разные («ВЕРСИЯ со С»), а заголовки заданы платформой.

| Вкладка | Признак в заголовке | Что берётся |
|---|---|---|
| Справочник | есть ячейка «Skills» | названия из этой колонки |
| Развесовка | есть ячейки «Проект» и «Задание» | навыки — колонки между ними и «check» |

Регистр и лишние пробелы в заголовках не различаются.

**Справочник, подробнее** (`ingestion.catalog_names`):

- колонка сразу после «Skills» считается признаком доступности, **только если у неё нет заголовка**. Навык со
  значением «FALSE», «ложь», «нет» или «0» в справочник не входит. Колонка с заголовком («Описание») ничего не решает;
- повтор названия берётся один раз; название длиннее 100 знаков — заметка, а не навык;
- если вкладок с колонкой «Skills» несколько, справочник **не берётся ни с одной**, и об этом сказано. Скрытая
  вкладка в счёт не идёт, пока есть видимая. Причина: с чужим списком каждый настоящий навык оказался бы «не из
  справочника»;
- вкладка «УП» справочником не считается, даже если в ней есть колонка «Skills».

**Чья вкладка развесовки** (`ingestion.attach_skills`). Вкладка относится к плану, если на ней есть блок хотя бы одного
проекта этого плана — **по коду**. Так вкладка экзаменов отсеивается сама, без правила про её название: кодов проектов
на ней нет. Коды сравниваются через одну функцию (`skills.code_of`): пробелы и переносы внутри кода не различаются,
регистр различается.

Из вкладок плана скрытые берутся, только если видимых нет: скрытые вкладки паспорта — формы и образцы.

### 3.3. Несколько вкладок развесовки

В «Батоне» плану принадлежат две — текущая и «OLD». Какая верна, код не знает, и **не выбирает**: выбрать не ту
значит молча подставить устаревшие навыки.

1. После загрузки книги навыки проектов пусты, в карточке плана — сообщение и список «Вкладка развесовки навыков».
2. Методолог выбирает вкладку. Страница отправляет **тот же файл** ещё раз с полем `skills_tab`.
3. Приходит план с навыками. В форме меняется **только поле «Навыки»**; выбранный проект и всё, что набрано руками,
   остаётся.
4. «Не выбрана» поле «Навыки» не трогает.

Файл страница держит в памяти, и только вместе с планом, который из него прочитан. После перезагрузки страницы файла
нет: список закрыт, подсказка «Чтобы выбрать вкладку, загрузите книгу снова».

Одна вкладка плана — выбирать нечего, она читается сразу.

### 3.4. Разбор блока

`skills.parse_blocks`. Блок начинается со строки, в которой заполнена колонка «Проект». Если код повторён в каждой
строке блока — это тот же блок. Если код встречается снова после другого блока — это повтор: взят первый блок, о
втором сказано.

Строка блока определяется подписью в колонке «Задание» (`skills.line_of`):

| Подпись | Чем считается |
|---|---|
| `all` | доли навыков основной части |
| `Bonus all`, `Бонус all` | доли навыков бонусной части |
| `check`, `Bonus check` | суммы самой вкладки — **не читаются**: код считает суммы сам |
| начинается с `Bonus` / `Бонус`: `Bonus 01`, `Bonus01`, `Bonus_02` | бонусное задание |
| любая другая: `01`, `1`, `Блок 1` | основное задание; подпись сохраняется как есть |

`Bonuses` — название задания, а не бонус: после слова должна быть не буква.

Ячейка с долей (`skills.number`):

- пустая — 0;
- запятая и точка — десятичный знак: `0,25` и `0.25`;
- число должно быть записано как в таблице. «25%», «0_1», «١», «nan» — не доли;
- значение округляется до четырёх знаков и только потом сверяется с диапазоном 0…1. `1,0000000000000002`, которое
  оставляет формула, — это 1; `0,125` остаётся `0,125`;
- хранятся только ненулевые доли.

Заголовок навыка, разбитый на две строки, — одно название. Что стоит правее колонки «check» — пометки самой вкладки,
не навыки.

## 4. Что проверяется

### 4.1. Блок проекта

`skills.block_issues`. Основная и бонусная часть проверяются отдельно, одними правилами. Допуск суммы — 0,01: 0,99 и
1,01 проходят, 0,9899 и 1,0101 — нет.

| Что не так | Почему это важно |
|---|---|
| В `all` нет ни одной доли | у проекта нет навыков: платформа его не примет |
| Задания есть, а долей в `all` нет | делить между заданиями нечего |
| Сумма долей в `all` ≠ 1 | платформа отклонит |
| У навыка с долей сумма по заданиям ≠ 1 | часть баллов навыка не досталась ни одному заданию, или роздано больше, чем есть |
| Задания дают навык, у которого нет доли в `all` | задание «учит» навыку, которого у проекта нет |
| Задание не получает ни одного навыка проекта | за задание не начисляется ничего |
| Навыка нет в справочнике | платформа отклонит; код называет до трёх ближайших справочных названий и **ничего не заменяет сам** |
| В ячейке не доля от 0 до 1 | вкладка записана иначе (25 вместо 0,25) или в ячейке текст |
| Вторая строка `all`, повторная колонка навыка | берётся первая, о второй сказано: молча заменить — потерять данные |

Проект, у которого в части нет заданий (ещё не разбит на задания), замечаний о заданиях не получает: делить пока
нечего.

Автоматической «подгонки» суммы до 1 нет. Код показывает расхождение, правит человек.

### 4.2. План в целом

- у каких проектов плана развесовки нет;
- какие коды вкладки не найдены в УП (опечатка в коде, переименованный проект, проект другой программы);
- код, который встречается на вкладке дважды.

### 4.3. Навыки задания перед запуском

`validation.check_skill_names`. Когда план загружен из книги со справочником, названия из поля «Навыки» формы
сверяются со справочником: без учёта регистра и лишних пробелов, целиком. Разделители — перенос строки, запятая, точка
с запятой; сверяются первые 50 названий.

Незнакомое название — замечание в проверке входных данных («Навыки задания, которых нет в справочнике платформы: …»)
с ближайшими справочными названиями.

**Тяжесть.** Замечания к блокам и к плану (4.1, 4.2) — заметки в карточке плана: ошибка в развесовке чужого проекта
не должна мешать готовить свой. Замечание 4.3 — предупреждение в проверке входных данных. Запуск оно **не блокирует**:
в модуле все замечания ко входам сейчас предупреждения (`validation.input_review_findings`).

## 5. Что сохраняется

Всё лежит в плане (`concept/models.py`, `Curriculum`) и сохраняется вместе с запуском; схема сохранённых файлов — 2.

| Поле `Curriculum` | Содержимое |
|---|---|
| `skill_catalog` | названия справочника, до 1000 |
| `skill_tabs` | вкладки развесовки этого плана, из которых можно выбрать |
| `skills_tab` | вкладка, из которой прочитаны навыки; пусто — не выбрана или её нет |
| `skill_blocks` | блоки проектов плана |
| `skill_notes` | что сказать методологу о развесовке |

И одно поле строки плана: `CurriculumRow.skills` — названия навыков проекта, по одному в строке. Сначала навыки с долей
в `all`, затем те, что есть только в `Bonus all`. Если в самой вкладке «УП» есть колонка навыков («Список навыков»,
«Навыки»), строка оставляет свои, из вкладки развесовки они не подставляются.

Блок проекта (`SkillBlock`), как он хранится:

```json
{
  "code": "D1P1_Terminal",
  "main": {
    "shares": {"Git": 0.2, "Python": 0.3, "Network & system administration": 0.3, "Problem solving": 0.2},
    "tasks": [
      {"label": "01", "shares": {"Git": 0.2, "Network & system administration": 0.15}},
      {"label": "02", "shares": {"Python": 0.1, "Network & system administration": 0.2, "Problem solving": 0.3}}
    ]
  },
  "bonus": {
    "shares": {"Git": 0.1, "Python": 0.5, "Network & system administration": 0.1, "Problem solving": 0.3},
    "tasks": [
      {"label": "Bonus 01", "shares": {"Git": 0.5, "Python": 0.4, "Network & system administration": 0.5, "Problem solving": 0.35}}
    ]
  },
  "issues": []
}
```

В примере списки заданий сокращены: в основной части блока их шесть, в бонусной два.

`issues` — замечания к блоку из раздела 4.1.

`skill_notes` хранятся отдельно от `warnings` намеренно. Предупреждения импорта уходят моделям как ограничения плана
как источника («часы пересчитаны из академических»). Суммы в развесовке соседних проектов к подготовке этого проекта
отношения не имеют, и модели их не видят.

## 6. Где это используется дальше

Дальше идут **названия навыков** — во все части модуля — и **доли навыков в проекте** (строки `all` и `Bonus all`) — в
развесовку замысла (6.8). Доли по заданиям из паспорта дальше не идут: задания готовящегося проекта придумывает
замысел, и делит навыки между ними тоже он.

Цепочка: вкладка развесовки → `CurriculumRow.skills` каждого проекта → при выборе проекта поле формы «Навыки»
(`Brief.skills`). После этого у модуля два источника: навыки **этого** проекта из формы и навыки **всех** проектов из
плана.

### 6.1. Карточка плана на странице

`static/chat.js`, `renderCurriculum`. Показывает список выбора вкладки (если их несколько) и заметки о развесовке
(`skill_notes`) вместе с предупреждениями импорта.

### 6.2. Поле «Навыки» формы

`static/chat.js`, `applyRow`. При выборе проекта поле заполняется навыками строки плана. Методолог может править его
руками. До чтения развесовки у планов из паспорта это поле открывалось пустым.

**Флажок «Бонусное задание».** Если у проекта на выбранной вкладке развесовки есть бонусная часть (строка `Bonus all`
с долями или строки `Bonus 01…`), строка плана получает признак `CurriculumRow.bonus`, и форма открывается с
включённым флажком: план ждёт от проекта бонусные задания, и замысел без них получил бы замечание «в УП есть бонусная
часть, а бонусных заданий нет». Правила:

- выбор другого проекта ставит флажок по этому проекту — включает или снимает;
- выбор вкладки развесовки после выбора проекта флажок только включает и никогда не снимает поставленный руками;
- план без вкладки развесовки (CSV, книга с несколькими вкладками, пока ни одна не выбрана) о бонусе ничего не знает —
  флажок остаётся таким, каким его оставил методолог.

Поле редактируется и в чате после запуска: «Получаемые навыки» в списке полей задания (`concept/thread.py`, `FIELDS`).
Правило для модели чата (`concept/prompts/dialogue.md`): в многострочных полях незатронутые строки сохраняются дословно
и в прежнем порядке.

### 6.3. Путь участника: что новое, что было, что понадобится

`concept/input_semantics.py`, `program_map`. Код сравнивает навыки этого проекта с навыками проектов до и после него
по плану и считает три списка:

| Список | Что в нём | Как считается |
|---|---|---|
| `skills_practised_before` | навыки проекта, которые уже были в более ранних проектах | название есть у проекта выше по плану |
| `skills_new` | навыки, которые в программе встречаются впервые | названия нет ни у одного проекта выше |
| `skills_used_later` | навыки проекта, которые понадобятся дальше, с названиями проектов и их числом | название есть у проектов ниже по плану |

Названия сравниваются через `_key`: регистр, пробелы, дефисы и запятые не различаются, «ё» равно «е», опечатка
«Analisys» равна «Analysis». Знаки `+` и `#` различаются: «C», «C++» и «C#» — три навыка.

Сравниваются только проекты: экзамены плана в эти три списка не входят (`input_semantics.projects`).

Эти три списка используются в четырёх местах:

1. **Страница, блок «Путь участника»** (`static/chat.js`, `learnerPath`): «Уже встречались раньше», «Впервые в
   программе», «Понадобятся дальше». У каждого прошлого проекта в списке показаны его навыки и инструменты.
2. **Запросы к моделям** (`concept/planning.py`): списки уходят в `computed_state.program_map` — раздел, который
   посчитан кодом и который модель не пересчитывает.
3. **Разбор входов** (`concept/prompts/interpreter.md`): по ним модель пишет `learner_path.before` — что участник уже
   прошёл и что из этого нужно этому проекту — и `next_needs` — что понадобится следующим проектам.
4. **Передача генератору контента** (`bridge.py`): три строки текста — «Навыки, встречавшиеся раньше: …», «Навыки
   впервые: …», «Понадобятся дальше: навык — «проект»».

Практический смысл: навык «впервые» требует в проекте объяснения и примера; навык «уже встречался» можно использовать
без введения; навык, который «понадобится дальше», проект обязан довести до уровня, на который опирается следующий.
До чтения развесовки у планов из паспорта все три списка были пусты: навыков не было ни у одной строки.

### 6.4. Карта программы для моделей

`concept/planning.py`, `MAP_FIELDS`. Навыки каждого проекта плана уходят моделям в `curriculum_map` вместе с названием,
описанием, ОР, инструментами и часами. Модель видит, чему учат соседние проекты.

### 6.5. Разбор входов

`concept/prompts/interpreter.md`, модель-интерпретатор:

- `skills` для неё — **получаемые** навыки, а не входная подготовка: в аудиторию как данность они не попадают;
- **сомнительные навыки** (`doubtful_skills`): навык из УП, который по смыслу не относится ни к теме проекта, ни к
  блоку и похож на ошибку или сдвиг колонки. Модель помечает его и задаёт методологу неблокирующий вопрос, учитывать
  ли его. Код проверяет, что помеченный навык действительно есть в навыках строки УП буквально
  (`validation.check_program_place`): выдумать сомнительный навык модель не может.

### 6.6. Замысел

Модель замысла получает навыки в задании (`brief.skills`), в карте программы и — с правил 1.1 — отдельно, в
`computed_state.project_skills`: названия так, как их сравнивает код, и доли из УП. Для каждого задания она называет
навыки проекта, которые задание отрабатывает, с весом от 1 до 5 (`TaskPlan.skills`). Подробно — 6.8.

### 6.7. Генератор контента

`bridge.py` → `content/handoff.py` (`ConceptHandoff.skills`) → `content/writer.py`. Навыки проекта уходят модели,
которая пишет аннотацию, задания и теорию. Правило аннотации (`content/prompts/summary.md`): в ней сказано, какие
знания и навыки получит участник.

С 05.10.2026 вместе с названиями передаётся посчитанный блок развесовки замысла (`ConceptHandoff.skill_table` — строки
вкладки, те же, что в выгрузке) и то, что в нём не так (`ConceptHandoff.skill_gaps`). Модели, которые пишут тексты,
блок не получают, и в репозиторий участника он не попадает: это данные для паспорта, а не для участника.

**Готов ли блок, решает этап, который его сделал.** `bridge.handoff` спрашивает `skills.gaps(block, навыки формы)`:

- навыки формы, которые не достались ни одному заданию;
- всё, что модуль сказал бы об этом блоке, прочитав его из паспорта (`skills.block_issues`, раздел 4.1): сумма долей не
  равна 1, у навыка есть доля в проекте, а задания его не делят, задания дают навык, у которого в этой части нет доли,
  задание без навыков проекта.

Блок, на который модуль пожаловался бы при чтении, готовым не называется. На этапе контента это одна строка карточки
«Что получил генератор» (`content/handoff.py`, `skills_row`); сама она блок не судит:

| Строка «Навыки» | Отметка | Когда |
|---|---|---|
| «3, разложены по заданиям: блок развесовки для паспорта готов» | зелёная | `skill_gaps` пуст; под строкой — доли навыков в проекте, бонусная часть помечена «бонус:» |
| «3, блок развесовки требует правки» | пробел | под строкой — что не так: «ни одному заданию не достались: «SQL»», «основная часть: «Python» — доля 0,8, по заданиям сумма 0 вместо 1»… |
| «3, блок развесовки по заданиям не передан» | пробел | замысел на правилах до 1.1 либо черновик контента начат до 05.10.2026 |
| «не заданы» | пробел | поле «Навыки» пустое |

Список замечаний обрезается на 40 (`MAX_GAPS`). `content/` не импортирует `concept/`: проверки вызывает мост.

### 6.8. Развесовка замысла

Задания готовящегося проекта придумывает замысел, поэтому доли по заданиям из паспорта к нему не подходят: их надо
посчитать заново — для его заданий.

**Кто что решает.** Какое задание про какой навык — суждение модели замысла: вес от 1 до 5 на пару «задание — навык»
(1 — касается, 3 — отрабатывает наравне с другим, 5 — задание в основном про него). Доли считает код. Модель долей не
пишет: сумму до единицы она не держит, а при весах несходящуюся раскладку нельзя выразить.

**Как считается** (`skills.divide`, `skills.spread`, `skills.exact`):

1. Навыки проекта — названия из поля «Навыки» формы.
2. Доли навыков в проекте — из строки `all` блока проекта в паспорте, как есть. Если блока нет или в форме другой набор
   навыков, чем в блоке, — из весов: доля навыка равна его части в сумме «вес × часы» всех заданий.
3. Каждый навык делится между заданиями пропорционально «вес × часы задания»: вес говорит, насколько задание про
   навык, часы — насколько задание велико.
4. Доли округляются до сотых так, чтобы сумма была ровно 1: оставшиеся после округления сотые получают те, кто
   больше потерял.
5. Основные и бонусные задания (в замысле — задания с пометкой «Бонус») считаются отдельно: «01», «02»… и
   «Bonus 01»…

Пример. Навыки «Git» и «Python», два задания: часовое с весом Git 5 и восьмичасовое с весами Git 3 и Python 3.
«Вес × часы»: Git — 5 и 24, Python — 24. Git делится 17% и 83%, Python целиком у второго задания; в проекте Git — 55%,
Python — 45%.

**Что получается.** Тот же блок, что на вкладке паспорта (`Run.skill_block`), сохранённый с запуском:

- на странице — метки навыков у каждого задания и таблица «Развесовка навыков по заданиям» в процентах;
- в файле «Скачать текст» — блок строками вкладки (`all`, задания, `check`, `Bonus all`…);
- по ссылке «Скачать блок для паспорта (CSV)» под таблицей (`GET /api/runs/{id}/export/skills`, `skills.sheet`) — тот
  же блок файлом `skills.csv`, который открывает Excel и Google Таблицы: UTF-8 с меткой порядка байтов, «;» между
  ячейками, запятая в числах. Блок вставляется на вкладку развесовки без пересчёта: прочитанный обратно
  (`skills.parse_blocks`), файл даёт тот же блок, что хранится у запуска. Ячейка, которая начинается с «=», «+», «-»
  или «@», пишется текстом — с апострофом впереди: название навыка приходит из паспорта, который мог составить кто-то
  другой, а таблица выполнила бы такую ячейку как формулу;
- на этапе контента — строка «Навыки» карточки: готов блок для паспорта или что в нём править (6.7).

**Что проверяется** — раздел 7.4. Суммы не проверяются: их считал код.

**Два замечания о весах** (добавлены по итогам прогона на модели 05.10.2026). Блок может быть верным по суммам и при
этом описывать другой проект, чем план.

*Расхождение с планом* — когда в УП у проекта есть доли. Код считает, какую часть всей работы основных заданий
(«вес × часы») занимает каждый навык (`Divided.weighed`), и сравнивает с долей из строки `all`. Расхождение в 10
процентных пунктов и больше называется: «Problem solving — 36% при 20% в УП». В блок при этом идут доли из УП —
замечание говорит, что задания замысла про другое, чем план. Разница округляется до сотой пункта и только потом
сравнивается; доля плана показана как есть («42,5%»). Две предыдущие версии сравнения ошибались на границе: сравнение
дробей — из-за шума вычислений (0,3 − 0,2 в числах с плавающей точкой — не 0,1), сравнение округлённых процентов — на
долях с половиной процента (42,5% округлялось до 42, а парные 57,5% — до 57).

*«Только касаются»* — наибольший вес навыка среди основных заданий ниже 3 (`Divided.peak`): навык стоит в списке
проекта, одно задание с весом 1 получает его целиком, и проверка «навык никто не отрабатывает» молчит. Называется:

- если долей в УП нет — для любого навыка проекта;
- если доли есть — только для навыка, которому план отводит 0,3 проекта и больше (`NOTABLE`).

Порог 0,3 — не оценка важности, а граница выполнимости. Навык с малой долей по праву только затронут; если требовать от
него веса 3, он выходит за план больше чем на 10 пунктов, и оба замечания сразу снять нельзя — так вела себя первая
версия. Без этого замечания при долях УП (вторая версия) молча проходил замысел, где все веса низкие и пропорции плана
соблюдены: «Git 1, Python 1» при плане 0,5 / 0,5. Проверено перебором (`tests/concept/test_concept_skills.py`): для
проекта из двух заданий веса без замечаний есть при любом плане из двух навыков в целых процентах; для проекта из
одного задания — при долях от 8% до 92%. Ниже 8% одно задание выразить долю не может: шкала 1–5 даёт самое меньшее
шестую часть.

| «Сомнительный навык не найден в колонке навыков УП» | модель пометила сомнительным навык, которого в УП нет | замечание к ответу модели, исправляется повтором шага |

### 7.4. В проверке замысла: навыки по заданиям

| Сообщение | Что значит | Что делать |
|---|---|---|
| «Задание 2 называет навыки не из навыков проекта: «Kotlin»» | модель назвала навык, которого нет в поле «Навыки» | повторить подготовку или убрать навык замечанием к замыслу; если навык нужен проекту — добавить его в поле «Навыки» |
| «Задание 1 называет один навык дважды, в разном написании: «git» — учтён первый вес» | два веса одного навыка | оставить один |
| «Навыки проекта не отрабатывает ни одно основное задание: «SQL»» | навык проекта никто не получит: основную часть делает каждый участник | добавить действие и сдачу по навыку в задание либо убрать навык из поля «Навыки» |
| «Навыки проекта не отрабатывает ни одно бонусное задание: …» | навык бонусной части УП не достаётся ни одному бонусному заданию | то же для бонусных заданий |
| «В УП у проекта есть бонусная часть развесовки (…), а бонусных заданий в замысле нет» | бонус в задании выключен, а в паспорте у проекта есть `Bonus all` | разрешить бонус либо убрать строку `Bonus all` у проекта |
| «Основные задания отрабатывают навыки, у которых в этой части развесовки УП нет доли: «SQL»» | навык в УП отведён другой части | убрать навык у заданий этой части или добавить его долю на вкладку |
| «Доли навыков проекта на вкладке развесовки (основная часть) в сумме дают 0,8, а не 1…» | ошибка в строке `all` паспорта: блок с такой строкой платформа не примет | исправить строку `all` |
| «Доля навыка в проекте меньше сотой и округлилась до нуля…» | у навыка слишком малый вес | убрать навык у задания или дать больший вес |
| «Задания, которые не отрабатывают ни одного навыка проекта: 2, 4…» | за задание не начисляется ничего | указать навык или объединить задание с соседним |
| «Доли навыков в проекте посчитаны из весов заданий, а не взяты из УП: в поле «Навыки» другой набор навыков…» | набор в форме изменён относительно блока УП | вернуть набор из УП либо исправить блок на вкладке |
| «По весам и часам заданий навыки занимают другую часть работы проекта, чем в УП: «Problem solving» — 36% при 20% в УП» | задания замысла про другое, чем план: расхождение 10 пунктов и больше. В блок идут доли из УП | проверить веса заданий замечанием к замыслу либо исправить строку `all` в паспорте |
| «Навыков проекта основные задания только касаются (вес ниже 3 в каждом задании): «Python» — доля в УП 0,5» | навык из списка ни в одном основном задании не отрабатывается. При долях из УП — только о навыке с долей 0,3 и больше (тогда доля названа) | сделать навык заметной частью хотя бы одного задания либо убрать его из поля «Навыки» |

Первые три — блокеры, остальные — замечания; в демонстрационном режиме все показываются как замечания.

## 8. Границы чтения

Два правила. **Вкладка рядом с планом плану не отказывает.** И **план, который загрузился, можно запустить**: он целиком
уходит на сервер с каждым запросом на запуск, а у запроса лимит 800 тыс. знаков (`StartRequest.input_limits`).

| Случай | Что происходит |
|---|---|
| Вкладка развесовки или справочника длиннее 5000 строк | пропущена и названа, остальное прочитано |
| Вкладок развесовки этого плана больше 10 | на выбор первые 10; чужие и скрытые в счёт не идут |
| В справочнике больше 1000 названий | взяты первые 1000 |
| В части блока больше 50 заданий | прочитаны первые 50 |
| Код длиннее 100 знаков, подпись задания длиннее 60, название навыка длиннее 100 | это заметка, оставленная в таблице, а не строка и не навык: пропущена |
| В блоке больше трёх ячеек с не-долями | названы первые три, остальные посчитаны |
| Кодов вкладки, которых нет в УП, больше 10 | названы первые 10, остальные посчитаны |
| Повтор кода проекта плана или строки `all` | сказано один раз, сколько бы раз он ни стоял |
| Блоки тяжелее 250 тыс. знаков | доли не сохраняются, названия навыков берутся |
| Заметок больше 50 тыс. знаков | показаны первые, остальные посчитаны |
| План после разбора не проходит лимиты модели данных | отказ словами: «Учебный план не удалось разобрать: …» |

Каждое обрезание сказано в заметках. Ближайшие справочные названия ищутся один раз на название вкладки, а не на каждый
блок: 200 проектов с незнакомыми навыками раньше не укладывались в 30 секунд, отведённые на файл.

## 10. Чего нет

- Проверки проверяющей модели на заведомо неверном весе: в прогоне она о навыках не сказала ничего.
- В комплекте результата (репозиторий участника: README, check-list, материалы) таблицы развесовки нет. Блок есть на
  странице, в файле «Скачать текст», в файле `skills.csv` и в передаче этапу контента (6.7); модели, пишущие тексты,
  его не получают.
- Замечание «только касаются» при долях из УП выдаётся только для навыка с долей от 0,3 (6.8): навык с долей 10% в УП
  и 3% работы в замысле пройдёт молча — до порога в 10 пунктов.
- Проект из одного задания с навыком, которому УП отводит меньше 8%, всегда получает замечание о расхождении: шкала
  весов 1–5 меньше шестой части одного задания не выражает.
- Пороги замечаний (вес 3, 10 пунктов, доля 0,3) выбраны по одному прогону на трёх запусках и перебором на двух
  навыках; на повторных прогонах не проверены.
- Ячейка `skills.csv`, записанная текстом из-за знака формулы в начале, читается обратно вместе с апострофом: для
  такого названия файл не равен блоку.
- Навык с названием «check» в блок не укладывается: так называется служебный столбец вкладки, и блок с таким навыком
  обратно не читается.
- В черновике контента, начатом до 05.10.2026, блока нет, даже если у запуска он посчитан: черновик хранит свой снимок
  передачи. Карточка говорит об этом прямо («не передан»).
- XP не считается: в шаблоне паспорта его нет.
- Отдельного поля для правки веса в чате нет: просьба «в задании 3 главный навык — SQL» идёт общим путём замечаний к
  замыслу.
- В форме нет выбора навыка из справочника: поле «Навыки» — текст, названия сверяются после ввода.
- Пустое поле «Навыки» запуск не блокирует и вопроса не вызывает; развесовки у такого проекта нет.
- Развесовка из CSV не читается.
- Вкладку развесовки с заголовком ниже 50-й строки или без колонок «Проект» и «Задание» код не найдёт.
- Навык в форме сверяется со справочником целиком: «Git, GitHub» через запятую — два навыка.
- Две вкладки развесовки одного плана с названиями, разными только пробелом в конце, в списке выглядят одинаково;
  выбирается первая.
- У запуска, начатого на правилах до 1.1, развесовки замысла нет.

## 11. Как проверить руками

Загрузить книгу паспорта на странице модуля: в карточке плана появятся заметки о развесовке и, если вкладок несколько,
список выбора. Выбрать вкладку и проект, у которого в ней есть `Bonus all`: флажок «Бонусное задание» включится сам.
После подготовки замысла на правилах 1.1 под таблицей «Развесовка навыков по заданиям» — ссылка «Скачать блок для
паспорта (CSV)»; файл открывается в Excel без настройки импорта.

Без страницы:

```bash
# тесты чтения и проверок, плана из паспорта, расчёта долей и развесовки замысла
python -m pytest project_generator_lab/tests/concept/test_passport_skills.py project_generator_lab/tests/concept/test_passport_plan.py \
    project_generator_lab/tests/concept/test_skill_spread.py project_generator_lab/tests/concept/test_concept_skills.py -q

# тесты страницы
node --test project_generator_lab/tests/js/*.test.mjs

# что прочитано из книги: вкладки, заметки, навыки проектов (bash или WSL)
python - <<'EOF'
from pathlib import Path
from project_generator_lab.concept.ingestion import parse_curriculum

plan = parse_curriculum("Паспорт.xlsx", Path("Паспорт.xlsx").read_bytes(), "Развесовка skills - ВЕРСИЯ со С")
print(plan.skill_tabs, len(plan.skill_catalog))
print(*plan.skill_notes, sep="\n")
for row in plan.rows:
    print(row.code, "|", row.skills.replace("\n", ", "))
EOF

# сравнение моделей на строке плана с навыками из выбранной вкладки (платный прогон); в отчёте — веса,
# которые модель дала заданиям, и блок, который посчитал код
python -m project_generator_lab.concept.benchmark --plan Паспорт.xlsx --row 1 --skills-tab "Развесовка skills - ВЕРСИЯ со С"
```
