# Подготовка проекта: замысел и контент

Отдельный локальный прототип нового генератора: замысел проекта и учебный контент в одном чате. Повторяет компоновку и оформление формы `static/index.html`: входы слева, результат справа, разделы УП / контекст / параметры / содержание / материалы. Действующий генератор и его БД не меняются.

Изменения 02.11.2026: [диалог, приоритет источников, пакетный черновик, большие корпуса и настройки написания](docs/collaboration-1.2.md). Правила 1.2, контент 0.11, схема хранения 6; описание включает ограничения и совместимость старых проектов.

Новый контур: [проверка готового проекта по 56 критериям и финальный дашборд](docs/evaluation.md). Открывается из чата контента; оценки с цитатами, полнота проверки и экспериментальная рекомендация показаны отдельно. Сохранённые проекты и их согласование не меняются.

## Запуск

Из корня S21_content_factory:

```powershell
uv run --no-sync python -m uvicorn project_generator_lab.app:app --host 127.0.0.1 --port 8011
```

Открыть http://127.0.0.1:8011. Используются зависимости существующего проекта, дополнительных пакетов нет. Для подключения читаются существующие `POLZA_AI_API_KEY` и `POLZA_AI_BASE_URL` из корневого `.env`. Модель задаёт только `PROJECT_LAB_MODEL`, по умолчанию `openai/gpt-6-sol` (выбрана сравнением 27–28.09.2026); общая `POLZA_AI_MODEL` принадлежит основному генератору и на модуль не влияет. Все этапы — разбор входов, замысел, проверка и чат — идут на одной модели, если не задан `PROJECT_LAB_REVIEWER_MODEL`. Потолок ответа — `PROJECT_LAB_MAX_OUTPUT_TOKENS` (11 000), таймаут вызова — `PROJECT_LAB_TIMEOUT_SECONDS` (150 с); для моделей Claude нужны около 32 000 и 600. Ключи не копируются в папку и не передаются браузеру. Для отделения аккаунта задайте переменные окружения перед запуском; окружение имеет приоритет над `.env`.

Сервер предназначен только для локальной работы на 127.0.0.1. Запускать одним worker. Нет пользователей, подключения к БД УП и совместного редактирования. «Пример из проекта» читает локальную копию заполненного CSV, а не живую БД.

## Что можно сделать

1. Заполнить форму вручную или загрузить УП: CSV (выгрузка вкладки «УП» паспорта программы и два прежних формата) или саму книгу паспорта XLSX; выбрать блок и проект. Экзамены плана в списке видны, выбрать их нельзя.
2. Приложить DOCX/PDF/XLSX/текст/скрипты, проверить извлечённый текст, назначить роли файлов.
3. Получить карточку понимания входов. Проверить ОР, аудиторию, ограничения, роль проекта и материалы с основаниями. В демонстрационном режиме все замечания остаются предупреждениями: кнопка «Продолжить с предупреждениями» позволяет подготовить замысел для обсуждения. Непрочитанные файлы отмечены в реестре; работа продолжается по доступным данным без выдумывания их содержимого.
4. Подтвердить входы и подготовить замысел реальной моделью. Посмотреть цепочку ОР → действие → сдача → P2P и заключения по шести направлениям. При недоступности модели частичный результат сохраняется; имитационной генерации нет.
5. Внести уточнения и подготовить новую версию. Отличия входов и замысла сохраняются в данных запуска. Вкладка истории и формы решений по замечаниям временно убраны из интерфейса; ранее записанные решения сохранены в JSON, API продолжает их поддерживать.
6. Согласовать демонстрационный результат с любыми замечаниями, скачать Markdown и полный JSON. Предупреждения сохраняются после согласования.

## Схема работы

`получены входы → реестр чтения → карточка входов → согласование входов → замысел → проверка → решения методолога → согласован`

Версия правил 0.3. API `POST /api/runs` заканчивает первый этап в `input_review`; `POST /api/runs/{id}/confirm-inputs` идемпотентно запускает проектирование по сохранённой карточке. `POST /api/runs/{id}/feedback` записывает подтверждение или отклонение замечания с причиной. `parent_run_id` создаёт новую версию, не изменяя предыдущую; принадлежность родительского запуска проверяется. После утверждения замысла решения по замечаниям не меняются. Новая версия проверяется целиком, поскольку изменения могут повлиять на связанные ОР.

Реестр формируется кодом: SHA-256, статус чтения, число извлечённых и переданных фрагментов, непрочитанные части и ограничения. Ошибка чтения остаётся в комплекте как файл со статусом `failed`, пока методолог не заменит или не удалит его. Старые загрузки без статуса имеют `legacy_unknown`; обязательные материалы нужно загрузить заново. Статус `text_extracted` относится только к поддерживаемому текстовому слою и не подтверждает полноту изображений, запуск кода или содержимое внешних ссылок.

Ошибки модели оставляют запуск незавершённым; частичный замысел сохраняется. Перезапуск сервера помечает выполнявшиеся работы прерванными. Повтор запроса с тем же UUID не создаёт второй запуск. Одновременно допускаются два запуска, вызов провайдера ограничен таймаутом и одним повтором. Возврат пользователя на страницу восстанавливает сохранённый запуск.

Для неверных ссылок или неполного формата карточки и заключения допускается одна автоматическая попытка исправления на этап. Исходный и исправленный ответы сохраняются в `input_attempts` / `review_attempts`, каждый вызов имеет отдельную запись длительности и токенов. Все замечания к карточке, замыслу и заключению рекомендательные и не препятствуют продолжению или согласованию. Вопросы к методологу автоматически не заполняются. Обычный путь — три вызова оркестратора, максимум пять с исправлением ссылок обоих этапов. Каждый из них допускает ещё одну попытку исправления невалидного JSON по исходной схеме: максимум десять запросов модели, не считая транспортного повтора провайдера. Счётчик schema_repairs, суммарные токены и длительность обеих попыток отражаются в событии. Невалидный ответ не подменяется фиктивным успехом; после второй ошибки этап завершается с ошибкой.

Демонстрационная политика действует для всех новых и уже сохранённых запусков: замечания становятся предупреждениями при чтении без повторного обращения к модели и без перезаписи снимка. При подтверждении они сохраняются и передаются проектировщику и проверяющему. Разрешение продолжить не означает подтверждения спорных фактов. Старый запуск, остановленный из-за чтения файлов до создания карточки, можно продолжить кнопкой «Продолжить разбор входов». Сбой модели или отсутствие ещё не созданного результата не подменяются успешным завершением; изменённая форма требует новой версии, выполняющийся запрос нельзя запустить повторно.

## Обоснования вместо скрытых рассуждений

Показываются краткие публичные объяснения, источник факта, предлагаемые решения и противоречия. Скрытый chain-of-thought не запрашивается и не выводится. Журнал показывает фактические этапы, модель, длительность, входные/выходные токены. Денежная стоимость не вычисляется без проверенного тарифа. Версия промптов, исходные входы и выбранные фрагменты сохраняются в JSON запуска.

## Нужен ли консилиум

В версии 0.3 — интерпретация входов, проектировщик и существующий проверяющий: три ограниченных вызова одной настроенной модели с паузой для методолога после первого. Дополнительного общего критика нет. Проверяющий получает первичные основания, реестр, согласованную карточку и замысел; ошибки всё ещё могут быть общими. Код проверяет полноту направлений и ОР, существование источников и адресов заданий, наличие действия, сдачи и проверки. Содержательную корректность оценивают модель и методолог. Общий процент качества не рассчитывается. Несколько разных моделей имеет смысл сравнивать на размеченных примерах при устойчивых пропусках.

## Границы версии

Боевой модуль опубликован отдельно от основного генератора, за существующей авторизацией. Адреса, устройство размещения и откат: [deploy/README.md](deploy/README.md).

Разбор CSV проверен на паспорте из тестов действующего генератора: повторяющиеся колонки образовательных результатов объединяются, проекты без номера сохраняют порядок файла, диапазон размера группы берётся по верхней границе. Название блока наследуется внутри блока, цели предыдущего блока не переходят в новый. Выбранный блок передаётся из раздела 01 без повторного ввода в разделе 02. После обновления парсера ранее загруженный CSV нужно загрузить заново: локальный черновик хранит результат прежнего разбора.

Это совместимость корректных CSV, а не копия всех обходных правил старого импортера: строки с неверным количеством ячеек отклоняются с указанием записи. Нужен повторный экспорт CSV с корректными кавычками. Проверить текущую развёрнутую версию по ссылке без авторизации не удалось; сравнение выполнено с кодом и примерами в репозитории.

Внешний веб-поиск выполняется только по кнопке «Проверить актуальность» и только по замыслу (версия 0.6). При разборе и проектировании ссылки остаются непроверенными; модель составляет список потребностей в материалах. В приложенных справочных материалах используется простой поиск по совпадению слов, до десяти фрагментов на файл; UI сообщает охват. Обязательные требования передаются целиком, превышение бюджета останавливает подготовку с объяснением. Это baseline для оценки поиска, не полноценный RAG.

Читаются текст и таблицы DOCX, текстовый слой PDF, значения и формулы XLSX, исходные ячейки ноутбуков и обычные текстовые форматы. OCR, анализ изображений и исполнение кода не выполняются. Ограничения чтения видны в UI. До 4 МБ на файл, до 12 вложений, до 200 проектов в CSV. Входы сохраняются локально и отправляются настроенному LLM-провайдеру при запуске подготовки.

Согласование сохраняет снимок, но не запускает полный генератор. Нет автоизменения УП или стандартного шаблона контента.

## Уточнения интерпретации и проверки — 0.3

`input_semantics.py` передаёт одинаковые правила всем трём вызовам: получаемые навыки не являются входными требованиями, а опции дополнительного оформления не отменяют инструмент или артефакт, прямо требуемый ОР. Позиция в УП вычисляется из порядка записей; сама позиция не доказывает освоение темы.

Новый контракт ответа критика требует для каждого ОР: требуемое действие, запланированное действие, наблюдение пира и пробел. Проверяющий должен различать выбор и применение стратегии, сценарий встречи и её проведение, произвольную таблицу и работу с Excel-шаблоном. Будущие кейсы и шаблоны планируются как комплект для следующего этапа, с указанием создателя и действия слушателя.

`reconcile_review` проверяет внутреннюю согласованность заключения: положительный статус с явным пробелом, неверной связью заданий или отсутствующим основанием становится «нужно уточнить». Отображаемый итог строится из статусов; исходный ответ модели остаётся в `review_attempts`. Это не автоматическое доказательство педагогического качества: смысл действия оценивает модель и затем методолог.

Старые снимки сохраняются, новые поля проверки необязательны при чтении архива. Правила 0.3 применяются при создании новой версии входов. Продолжение ранее начатой версии использует сохранённые промпты. Все замечания по-прежнему рекомендательные.

В интерфейсе релиза 20260923-02 остаются сами замечания и основания. Поля подтверждения/отклонения замечаний и вкладка «Изменения» не показываются. Повторяющиеся пояснения о демонстрационном режиме убраны; подсказка под кнопками появляется только при изменённой форме. Данные истории и решений не удаляются, а согласование по-прежнему доступно с предупреждениями.

## Версия 0.4 — чат и правки задания

Главная страница `/` — светлый чат. Методолог заполняет главное (или загружает УП), получает разбор входов и вопросы, отвечает в чате. Каждый ответ превращается в карточку правок полей задания: было → стало, источник («Ответ на вопрос N», «Просьба методолога», «Предложение ИИ»). В задание правка попадает только после «Применить»; её можно исправить, отклонить или отменить. Прежний интерфейс доступен по `/classic`.

Задание (Brief) — единственный вход для разбора, замысла и проверки. Переписку получает только модель диалога (`prompts/dialogue.md`); модели разбора, замысла и проверки видят задание, а не историю чата. Черновик задания разбирается кнопкой «Разобрать версию N» как новый запуск с `parent_run_id`; прежние версии не меняются. Диалог хранится в `data/runs/threads/<id>.json`, записи только дописываются.

Что изменилось по обратной связи методологов:

- Стартовый уровень аудитории — отдельное поле (`start_level`: нулевой, базовый, средний, продвинутый) и «Что уже умеют» (`start_skills`). Пустой уровень — вопрос, а не новичок по умолчанию. Для нулевого уровня промпты запрещают настройку окружения и служебные файлы без основания. Из колонки «Уровень аудитории» уровень подставляется только при однозначном слове; иначе методолог выбирает сам.
- «Что должна дать программа» заменено на «ОР программы» и «Требования заказчика». Старое поле `program` сохраняется в старых снимках и передаётся модели, если новые пусты.
- Место проекта в программе считает код по порядку УП (проект N из M, блок, соседние проекты) и показывает методологу и моделям.
- Разбор CSV называет распознанные колонки, не найденные ключевые поля и нераспознанные колонки. Ошибка «нет колонки названия» перечисляет заголовки файла.
- Трудоёмкость считает код (`workload.py`), не модель. Нормы — в `config/workload.json` (черновые, меняются методологами; путь можно переопределить `PROJECT_LAB_WORKLOAD_NORMS`). Код рассчитывает допустимое число основных заданий и часы на задание до проектирования, передаёт это моделям в `computed_state` и после проектирования проверяет разбивку каждого задания (чтение, настройка, выполнение, ошибки и повторы, сдача): сумму, долю непрямых затрат для уровня, настройку в первом задании, число заданий. Структурные расхождения — blocker, отклонения от черновых норм — предупреждения.
- Остановка: `POST /api/runs/{id}/cancel` останавливает подготовку в безопасной точке; готовые этапы сохраняются, запуск помечается «остановлен». `POST /api/runs/{id}/resume` продолжает с незавершённого этапа: готовый замысел не генерируется повторно, повторяется только проверка. Полный сброс прогресса и кэша не реализован.
- Проверяющий может работать на отдельной модели: `PROJECT_LAB_REVIEWER_MODEL` (желательно другое семейство, сопоставимое по силе). Без переменной проверяет основная модель, как раньше.

## Версия 0.5 — правки по РГ 25.09.2026

Замечания Антона из рабочей группы и принцип «практика первична» (peer-to-peer, как в École 42).

Сейчас это черновики только из того, что сказано на встрече; дополняют их методисты. Файлы замораживаются в запуске, как промпты, и приходят всем моделям в `fixed_rules`.

## Версия 0.6 — маршрут в чате, место в учебном плане, актуальность

Правки по тесту 29.09.2026 на проекте «Бюджет IT проекта и составление сметы».

- **Что дальше — подсказки-чипсы.** Работа идёт в диалоге, как в чат-ассистенте. В конце ленты ассистент пишет, где сейчас работа, и предлагает чипсы: первым — шаг этапа, который код выбрал по состоянию версии («Подготовить замысел», «Учесть правки и подготовить замысел», «Применить правки и продолжить», «Согласовать замысел», «Продолжить»), дальше короткие пути: «Ответить на вопрос N», «Изменить задание…», «Проверить актуальность», «Скачать замысел». Нажатие на шаг этапа остаётся в истории репликой методолога, ассистент отвечает, что запустил. Чипс отправляет название шага, который видел методолог; если состояние успело измениться, сервер отказывает (`POST /api/threads/{id}/advance`).
- **«Дальше» в чате.** «Дальше», «продолжаем», «генерируй задания» и подобные короткие реплики модели не отправляются: код сразу выполняет следующий шаг. Если в сообщении есть и сведения, и просьба идти дальше («материалов нет, идём дальше»), модель делает правки и ставит `proceed`; переход ждёт решения по правкам. Согласование из чата не выполняется: оно фиксирует версию и остаётся кнопкой. Раньше «Генерируй задания» превращалось в правку поля «Комплект генератора».
- **Автопродолжение.** Новая версия, запущенная из чата или кнопкой «Учесть правки…», после разбора входов сама переходит к замыслу и проверке (`Run.auto_continue`), если в новом разборе нет важного вопроса. Важность берётся из исходного ответа модели: демонстрационный режим снимает блокировку только в показанной карточке.
- **Панель задания** больше не занимает треть экрана: открывается кнопкой «Задание» поверх чата. Действия этапов переехали из неё в чат; в панели остались поля, история, контекст и выгрузка.
- **Место в учебном плане** (`input_semantics.program_map`): проекты блока с часами и текущим, соседние проекты, часы до проекта, навыки из колонки УП — уже встречались, впервые, понадобятся дальше. Считает код; карточка показывается в чате сразу после входных данных, рядом — как связь понял интерпретатор. Та же карта приходит моделям в `computed_state.program_map`; проектировщик по правилу 0.6 называет, на какой проект блока опирается задание и кто использует его результат, но повтор навыка в колонке УП связью не считает.
- **Без выбора поля.** Выпадающий список «Поле: определить по смыслу» убран. Если сообщение можно отнести к нескольким полям по-разному, ассистент задаёт один вопрос и называет варианты.
- **Проверка актуальности** (`freshness.py`). Кнопка после замысла отправляет поисковой модели (`PROJECT_LAB_SEARCH_MODEL`, по умолчанию `perplexity/sonar-pro` через тот же ключ Polza) название, ОР, инструменты, сторителлинг и задания — без чата и материалов. Модель отмечает, что устарело (сервисы, тарифы, модели оплаты, версии, ссылки), и предлагает до трёх актуальных примеров для кейса. Ссылки в отчёт попадают только из источников, которые вернул провайдер: номера вне списка отбрасываются и считаются, пункт без единого источника получает «неясно». Задание отчёт не меняет; учесть пункт — сообщением в чат.

## Версия 0.7 — посторонний материал во входах

Если во входах есть текст, который не относится ни к проекту, ни к программе (рецепт выпечки в брифе продакт-менеджера, чужая переписка, реклама), интерпретатор кладёт его в `input_card.off_topic`: ID фрагмента, короткая цитата, весь посторонний текст дословно (`text`), почему не связан — и задаёт вопрос «Не учитывать …?». Для названия, описания и ОР вопрос важный, для файлов — обычный. Код оставляет только то, что действительно находится в указанном фрагменте. В чате — блок «Похоже, не относится к проекту» с местом (файл, строки) и кнопками «Не учитывать» / «Это нужно»; кнопки ничего не удаляют, они пишут ответ в поле ввода.

Фрагмент файла — не абзац: текстовый файл читается по 35 строк, поэтому рецепт обычно лежит в одном фрагменте с нужным брифом. Поэтому исключается текст, а не фрагмент. Решение методолога становится строкой в поле «Не учитывать фрагменты файлов» (`excluded_sources`): `<ID>: «текст» — почему`. Код вырезает ровно этот текст (переносы строк не важны), остальной текст фрагмента остаётся; текст, которого во фрагменте нет, не вырезается — предложение такой правки отклоняется в чате, а в предупреждениях запуска это видно. Исключить фрагмент целиком (`<ID> — почему`) можно, только если он короткий или посторонний текст занимает почти весь фрагмент. Посторонний текст в поле формы убирается правкой этого поля. Исключённое не видят интерпретатор, проектировщик и проверяющий, и мост не передаёт его генератору контента. Пока методолог не решил, проектировщик не строит на таком тексте задания. Если фрагмент нужен — запись в «Уточнения методолога», и он больше не помечается. Тесты: `tests/concept/test_off_topic.py`.

## Версия 0.8 — место в блоке: раскладка целей и рассуждение

Цели блока в УП написаны на весь блок. Раньше карточка «место в учебном плане» показывала их одним списком, и не было видно, что из этого берёт проект. Теперь:

- **Раскладка целей блока** (`input_card.block_goals`). Код нумерует цели по строкам ячейки (`program_map.block_goal_items`). Интерпретатор отдаёт каждую цель проекту блока: предыдущий / этот / следующий / сквозная / не видно — с названием проекта и признаком, по которому решил. Код проверяет, что разложены все цели по одному разу и проекты взяты из блока. В карточке — таблица «Цели блока — кто их закрывает» и кнопка «Поправить раскладку». Правка методолога записывается в поле задания «Цели блока: кто закрывает» (`block_scope`), и следующая версия переносит её как есть.
- **Рассуждение** (`input_card.program_reasoning`): 3–5 пунктов «факт УП → что из этого следует для заданий», с пометкой «задано / предложено» и основанием. Показывается в той же карточке вместо общих утверждений.
- **Навыки не по теме** (`input_card.doubtful_skills`): навыки из колонки УП, похожие на ошибку или сдвиг колонки (например, «Types and data structures» в проекте про риски). Код проверяет, что навык действительно есть в УП. Решение методолога — в «Уточнения методолога».
- **Проверка замысла кодом**, как для ОР: каждая цель «этого проекта» закрыта хотя бы одним основным заданием (`block_goal_numbers`), и задание не преподаёт заново цель предыдущего проекта. В замысле — строка «Цели блока этого проекта закрыты / не закрыты: …», в задании — «Цели блока» и «Связь с программой» (`program_link`: на что опирается, куда пойдёт результат). Проверяющий смотрит смысл, а не номера.
- **Дальше в контент**: мост передаёт цели задания и его связь с программой (`PlannedTask.block_goals`, `program_link`), а в `program_context` — раскладку словами и рассуждение. Автор задания использует их в ситуации, переходе и пояснении.

Тесты: `tests/concept/test_program_place.py`.

## Версия 0.9 — путь участника и чат одной задачи

**Путь участника вместо раскладки связей.** В 0.8 место в блоке объяснялось раскладкой целей блока по соседним проектам — методологу это мало что говорило. Причина была и в данных: модели передавались по другим проектам только название, описание, ОР и цели блока, без колонок навыков и инструментов, поэтому сказать, чем участник уже пользовался, она не могла. Теперь код собирает из УП по каждому проекту до этого ОР, навыки и инструменты (`input_semantics.learner_facts`: сколько проектов работали с каждым инструментом, какие инструменты этого проекта знакомы, какие новые впереди), а разбор входов пишет `learner_path`: `before` — что участник прошёл по УП, умениями, а не списком названий; `builds_on` — на что проект опирается и что не учит заново; `next_needs` — что понадобится в последующих проектах (не только в соседнем) и чему научить здесь, с ОР этого проекта. Код проверяет, что `next_needs` ссылается на реальные последующие проекты и реальные ОР. Замысел, проверяющий и генератор контента читают этот путь. Раскладка целей блока осталась для проверки покрытия, но в карточке свёрнута: открыты только цели этого проекта. Поправка методолога («Miro они ещё не проходили») записывается в «Уточнения» строкой «Путь участника: …» и учитывается в следующей версии.

**Чат одной задачи.** Чат — не общий ассистент, а помощник подготовки проекта. Модель сначала решает, что за сообщение (`kind`): просьба изменить, ответ на вопрос разбора (в форме «Вопрос N:» или своими словами), совет, вопрос (о проекте, маршруте, образовательных методиках, теме проекта) или не по теме. Дальше код держит её к этому: на вопрос — ответ без правок (правки, если модель их всё же предложила, отбрасываются с пометкой), не по теме — одно предложение и возврат к текущему шагу маршрута, который дописывает код. Под ответом видно, как чат понял сообщение («понял как: вопрос»), — ошибка распознавания видна сразу. То же в чате контента.

**Ответы на вопросы разбора.** Ответ, не ставший правкой, записывается в «Уточнения методолога» с вопросом — иначе следующая версия спросит снова. Номер вопроса из «Вопрос N:» читает код; у свободного ответа его называет модель (`answered`, первым полем ответа). Если после этого остались открытые вопросы, одним узким обращением к модели проверяется только «на какие вопросы отвечает сообщение». Защита кода: просьба пояснить вопрос и текст, скопированный из карточки (вопрос или его пояснение), — не ответ, в задание не пишутся (случай из локального прогона 30.09: пояснение вопроса, вставленное в чат с «поясни», было записано как ответ).

## Аудит 30.09.2026 — что исправлено и по каким принципам

Аудит шёл тремя независимыми проверками (безопасность, корректность данных, архитектура); исправления затем проверил отдельный проверяющий, который код не писал (шаблон «предлагающий — проверяющий» из книги Ли Боцзе, 1.3), — он нашёл ещё несколько дыр в самих исправлениях, они тоже закрыты. На каждое исправление — тест на то, что должно измениться, и на то, что не должно (граничный и удерживающий наборы, 1.3).

Ограждения на слое исполнения (1.2.5): действие с последствиями запускает код или человек, а не флаг из ответа модели.
- Переход дальше из сообщения чата — только если код прочёл просьбу в словах методолога (`core/intents.mentions_proceed`: последняя часть сообщения, не вопрос, без «сначала…», «и так далее» — не просьба). Флаг модели без этого — подсказка с кнопкой. Сообщение «нет, это не нужно, давай дальше» никогда не применяет ожидающее предложение. Платный поиск ссылок — только если методолог сам просит ссылки.
- Голое «да» после вопроса ассистента уходит модели как ответ; если ждёт предложение правок или прошлая реплика шла с правками («Подходит?»), «да»/«ок» обрабатывает код, как раньше.

Poka-yoke и слой данных (1.2.2, 1.2.5): неверное состояние невозможно по устройству.
- Правка черновика контента сначала проверяется на копии: значение, которое черновик не примет (аннотация короче 20 знаков), даже не предлагается; раньше оно сохранялось, файл переставал читаться и «Начать» откладывал его и писал всё заново.
- Предложение, текст под которым изменился (ручная правка, отмена, генерация), снимается с пометкой — оно не может висеть и ломать «Применить и продолжить». Отмена, дающая неверное задание, — отказ 409, а не ошибка 500.
- Проверки часов и сверки замечаний включаются сравнением версий (`since`), а не списком — список забыл 0.9 и выключил обе проверки.
- Новый ответ на тот же вопрос разбора заменяет прежнюю строку в «Уточнениях»; ответ пишется в одну строку.

Изоляция (1.2.5) и лимиты:
- Загруженные файлы разбираются в отдельном интерпретаторе (`core/isolated.py`) с лимитом памяти 600 МБ и 30 с процессора, без ключей сервера в окружении, со своей очередью. PDF на 100 КБ, разворачивающийся в 100 МБ, раньше ронял контейнер со всеми подготовками — теперь понятный отказ. XLSX с объявленным огромным листом отклоняется до чтения.
- Страницы по ссылкам на сервере открываются по тому адресу, который прошёл проверку (без повторного DNS — защита от подмены ответа DNS), с именем в Host и TLS, без переиспользования соединений между сайтами, не больше 512 КБ после распаковки, 20 с на страницу.
- Две подготовки и два текста одновременно на человека, а не на всех; потолок на сервер. Чужой файл — «не найден» до любых других проверок.

- Каждый вызов модели — одна строка журнала: этап, модель, время, токены, исправления формата, итог, чей запрос. Без текстов.

## Этап Г 01.10.2026 — правила 1.0, одно ядро чатов, схема файлов

Порядок полей схемы приведён к шагам: в карточке входов сначала `off_topic`, потом утверждения, место в программе, в конце `questions` и `summary` — вопрос, которого требует посторонний фрагмент или пустой стартовый уровень, пишется после того, как это найдено; в проверке — ОР, направления, замечания, в конце `summary` (раньше итог писался до проверки). Ничего не потеряно намеренно: отдельный проверяющий разложил старые промпты на атомарные правила и нашёл, где каждое в новых; потерянные и ослабленные (проверка `input_semantics` у проверяющего, «вопрос — только если методолог ещё не ответил», «да» после вопроса ассистента и др.) возвращены, повторная проверка — без замечаний. Версия правил `1.0`; запуски, начатые раньше, доживают на своих замороженных правилах.

Запрос разбора на УП из 24 проектов — 57 тыс. знаков вместо 87, из 48 — 97 вместо 161. Только для запусков на правилах 1.0.

**Одно ядро двух чатов** (`core/chat.py`). Что разрешает тип сообщения, возврат к проекту, когда «да» — ответ модели, когда чат переходит дальше — одно место для обоих чатов; раньше каждое исправление аудита делалось дважды. Тот же список «понял как: …» на странице для обоих чатов (в чате контента ответ назывался иначе).

**«Да» отвечает на сказанное последним.** Проверяющий нашёл: предложение «без Excel» ждёт, ассистент потом спрашивает «Добавить это в ограничения?», методолог отвечает «да» — и в ограничения записывалось «без Excel». Теперь «да» после вопроса ассистента уходит модели как ответ, даже если выше ждёт предложение; «ок» после реплики без вопроса ничего не решает и называет кнопку ожидающего предложения. Предложение принимает «да» сразу после него («Подходит?»), кнопка или «дальше».

**`dialogue.py` разбит**: `thread.py` (что хранится, схемы ответов), `patches.py` (правки задания), `answers.py` (ответы на вопросы разбора), `route.py` (маршрут и шаги), `dialogue.py` (HTTP и то, что получает модель).

**Ссылки.** Ссылка хранится в той форме, которую показывает предложение: Markdown, адрес Википедии со скобками, точка в конце больше не ломают отмену правки и не сохраняют обрезанный адрес. Предложение, которое больше нельзя применить (например, записанное прошлой версией), снимается при открытии черновика, а не блокирует «Применить правки».

**Схема сохранённых файлов** (`core/contracts.STORED_SCHEMA`, с 05.10.2026 — 2). Диалог, запуск и черновик контента хранят номер схемы. Файл с номером выше своего релиз читает без незнакомых полей (с записью в журнал) — откат на эту версию со следующей, если та только добавила поля, не требует восстановления данных. Файлы своей и прошлых версий читаются строго, как раньше. Тест сверяет отпечаток схемы с номером: изменили сохраняемые поля — тест падает, пока номер не увеличен.

**Блокировки** диалогов и черновиков живут, пока их держат, а не до перезапуска сервера.

## Паспорт программы как вход и нормы часов — 05.10.2026

Рабочая группа 02.10.2026 приняла стандартным входом паспорт программы — книгу с вкладками, образец — «Паспорт программы_Батон». Его вкладку «УП» прогнали через импорт и через расчёт часов как есть. Импорт не падал, но терял то, чего никто не видел; нормы часов расходились с проектами самой программы.

**Что терялось и что сделано.**

| Было | Стало |
|---|---|
| Два экзамена читались как индивидуальные проекты: их можно было выбрать, они считались в «проект N из M» | У строки плана есть вид — проект или экзамен (`CurriculumRow.kind`). Экзамен — когда «Формат» равен «экзамен»; если формата в плане нет вовсе — по слову «экзамен» в названии, и об этой догадке импорт пишет предупреждение с выходом («укажите формат»). Экзамен нельзя выбрать ни на странице, ни запросом к серверу. В «проект N из M», соседях и списке проектов блока экзаменов нет; в пути участника они остаются с пометкой, в счёте «в скольких проектах был инструмент» не участвуют. Часы плана считаются со всеми строками, как в «ВСЕГО» паспорта |
| «Тезисное тематическое наполнение проекта», «Кейсы…», «Формат проверки» не распознавались: форма открывалась с пустым описанием и пустой формой контроля | Тезисы — описание, кейсы — отдельное поле строки; в форму описание приходит как тезисы и кейсы вместе, потому что задание — единственный источник для разбора, замысла и чата. «Формат проверки» — форма контроля |
| У проекта не было кода (`D1P1_Terminal`): строку УП нечем связать с вкладкой развесовки | Поле `code`; моделям уходит в карте программы там, где оно есть |
| Сообщения «Краткое описание: колонка не найдена» и «Уровень аудитории: колонка не найдена» на каждом стандартном файле | Уровня аудитории в УП не бывает (он в брифе и концепции): об отсутствии колонки не сообщается; о колонке, которая есть и пуста, — сообщается |
| Прочерк в ячейке («-» у размера группы, кейсов экзамена) читался как значение | Ячейка из одного прочерка — пусто. Блок, цели блока, номер и название читаются как написано, как раньше |
| Только CSV одного листа | Книга XLSX: вкладка с проектами находится по заголовку (первая заполненная строка в первых 50), а не по названию или месту; скрытые вкладки — формы и образцы — берутся, только если видимой с проектами нет; при нескольких подходящих импорт не выбирает, а называет их. Книга разбирается в отдельном процессе с лимитами, как любой файл Office |
| В книге «2-4» человека в группе хранится как дата 02.04 | Дата в колонке размера группы читается обратно как диапазон |
| Только астрономические часы | Если астрономических часов в плане нет (нет колонки или в ней ни одной ячейки), берутся академические ×0,75 с предупреждением. Рядом с астрономическими академические не используются |

Заявленному размеру вкладки чтение не верит: у книги из Google Sheets его нет, а устаревший обрезал бы план. Читаются сами строки — не дальше 200 пустых подряд и не больше 5000.

**Нормы часов** (`concept/config/workload.json`). Из шести проектов «Батона» с развесовкой два получали блокер «число заданий вне диапазона»: 6 заданий на 6 ч и 6 заданий на 8 ч — это час на задание при нижней норме 1,5 ч. Ориентир числа заданий (часы / 3,75) давал 2–4, в программе их 5–6. Теперь: нижняя граница 1 ч; не больше 8 основных заданий в проекте (`main_tasks_max`); ориентир — число в файле (`tasks_typical`, 5), в пределах диапазона. Замечание называет причину: «больше, чем бывает в проекте (до 8 основных)» — отдельно от «не помещаются в часы». Обе новые нормы необязательны: без них расчёт прежний. Остальные числа не трогались и по-прежнему не сверены с временем участников; при заданиях в час норма «настройка в первом задании от 1 ч» для нулевого уровня даёт замечание на первом проекте программы — это вопрос к нормам, не к коду.

**Схема сохранённых файлов — 2.** У строки плана три новых поля; у плана — справочник навыков и развесовка (раздел ниже). Схема 2 ещё не выпускалась: номер у обоих изменений один. Файл старой схемы, прочитанный и сохранённый новым релизом, теперь получает номер этого релиза: раньше он оставался с прежним номером, но уже с новыми полями, и предыдущий релиз после отката отказывался его читать (нашёл независимый разбор). Лимит размера запуска считается без полей со значениями по умолчанию: запуск, сохранённый у самого лимита, не перестаёт открываться из-за новых полей.

**Сравнение моделей на своём плане:** `python -m project_generator_lab.concept.benchmark --plan <УП.csv или паспорт.xlsx> --row 3` — задание собирается так же, как его собирает форма.

**Чего нет.** Диапазон вида «12-15» в размере группы из книги Excel не восстанавливается (Excel хранит его как «1 декабря 2015»): такой план загружается выгрузкой в CSV. Прежняя страница `/classic` экзамены не отличает: отказ ей даёт сервер. План, оставшийся в браузере от прежней версии, экзамены не помечает, пока его не загрузят снова. Правила для моделей (промпты) не менялись: о том, что запись — экзамен, модели узнают из самих данных; прогон на модели на строках «Батона» ещё не делался.

**Как проверено.** Тесты на настоящей вкладке (`tests/concept/fixtures/baton_plan.csv`) и на книге, собранной так, как её сохраняют таблицы (числа дробями, без заявленного размера, с устаревшим размером); настоящая книга паспорта (21 вкладка) читается поле в поле как её CSV. Прежние планы — четыре файла примеров и фикстур — читаются как раньше, кроме задуманного: «Финальный экзамен (тестирование)» старой выгрузки теперь экзамен. Запросы к моделям для планов без кодов и экзаменов побайтно те же. Мутационный прогон по изменённым функциям (`ingestion`: `row_kind`, `astronomical`, `cell_text`, `plan_tab`, `workbook_records`; `input_semantics`: `projects`, `program_position`, `program_map`, `learner_facts`; `workload.budget`; `storage.parse_stored`; `validation.check_learner_path`): убито 817 из 841 (97%); выжившие — равнозначные замены (формат «F» вместо «f», значение по умолчанию, которое не достигается) и формулировки пояснений. Независимый проверяющий агент нашёл 5 существенных и 13 мелких замечаний; существенные и большая часть мелких исправлены, остальное — в «Чего нет».

## Развесовка навыков из паспорта — 05.10.2026

Подробное описание — что такое справочник и развесовка, как читаются, где используются дальше, что значит каждое сообщение: [`docs/skills.md`](docs/skills.md).

В паспорте навыки проекта записаны не в «УП», а на вкладке развесовки: какую долю каждого навыка даёт проект и как эта доля делится между заданиями. Платформа не примет проект, у которого суммы не равны единице или навык не из её справочника (вкладка «Available skills»). Форма открывалась с пустым полем «Навыки», а ошибки развесовки находились при заведении проекта на платформу. Теперь вкладки читает код, без модели.

**Что читается** (`concept/skills.py`, `concept/ingestion.py`).

- **Справочник** — вкладка с колонкой «Skills». Колонка сразу за ней, если у неё нет заголовка, — признак «доступен на платформе»: навык с «FALSE», «нет», «0» в справочник не входит. Колонка с заголовком ничего не решает. Если таких вкладок несколько (скрытые не в счёт, пока есть видимая), справочник не берётся ни с одной и об этом сказано: с чужим справочником каждый настоящий навык стал бы «не из справочника» и давал замечание на каждом запуске.
- **Развесовка** — вкладка с колонками «Проект» и «Задание»; навыки — колонки между ними и «check». Блок проекта начинается со строки с кодом (код, повторённый в каждой строке блока, — тот же блок): `all` — доли навыков в проекте, `01`…`N` — какая часть каждого навыка приходится на задание, `Bonus all` и `Bonus 01`… — то же для бонусной части, которая считается отдельно; `check` — суммы самой вкладки, они не читаются. Пустая ячейка — ноль.
- **Чья вкладка.** Вкладка относится к плану, если на ней есть блок хотя бы одного его проекта — по коду (`CurriculumRow.code`; пробелы внутри кода не различаются, регистр различается). Вкладка экзаменов паспорта так отсеивается сама, без правила про название. Скрытые берутся, только если видимых нет.
- **Несколько вкладок** (в «Батоне» — текущая и «OLD») — код не выбирает: навыки не читаются, пока методолог не выберет вкладку в карточке плана. Книга отправляется ещё раз с выбором (`skills_tab` у `POST /api/curriculum`); в форме меняется только поле «Навыки». Файл страница держит в памяти: после перезагрузки страницы выбор закрыт с подсказкой «загрузите книгу снова».
- Навыки проекта попадают в строку плана (`skills`) — и оттуда, как и раньше, в форму, в путь участника («новое / было раньше / понадобится дальше») и в запросы к моделям. План, у которого навыки названы в самой вкладке «УП», оставляет свои.

**Что проверяется.** По каждому блоку (`skills.block_issues`): сумма долей в `all` равна 1; у каждого навыка с долей сумма по заданиям равна 1; нет навыка, которому задания дают часть, а доли в проекте нет; нет задания без единого навыка проекта; название есть в справочнике — иначе названы ближайшие справочные, сам код ничего не заменяет. Допуск 0,01. Отдельно сообщается, у каких проектов плана развесовки нет и какие коды вкладки не нашлись в УП. Всё это — заметки в карточке плана (`Curriculum.skill_notes`): чужой проект с ошибкой в развесовке не мешает готовить свой. Навык задания, которого нет в справочнике (`validation.check_skill_names`), — замечание в проверке входных данных. Запуск оно не блокирует: все замечания ко входам в модуле — предупреждения (`validation.input_review_findings`).

На паспорте «Батона» это нашло: в текущей вкладке у `D6P3_Dataquery` бонусный навык «AI Engineering» с долей 0,2 не разнесён по заданиям, у `D7P4_Userflow` бонусные задания дают «DB & Data» и «SQL», которых нет в бонусной строке `all`; блок `D8-9P5_MCP` не соответствует ни одному коду УП; у пяти проектов из десяти развесовки нет.

**Чего вкладка не может сделать с планом.** Два правила. Вкладка рядом с планом не отказывает плану. И план, который загрузился, можно запустить: он целиком уходит на сервер с каждым запросом на запуск, а у запроса свой лимит (800 тыс. знаков).

| Случай | Что происходит |
|---|---|
| Вкладка развесовки или справочника длиннее 5000 строк | пропущена и названа |
| Вкладок развесовки этого плана больше 10 | на выбор первые 10, сказано. Чужие и скрытые вкладки в счёт не идут |
| В справочнике больше 1000 названий; в части блока больше 50 заданий | взято столько, сказано |
| Название навыка длиннее 100 знаков, код длиннее 100, подпись задания длиннее 60 | это заметка, оставленная в таблице (в «Батоне» — текст под блоками экзаменов), а не навык и не строка |
| Вкладка записана не долями (25 вместо 0,25) | в блоке названы первые три ячейки, остальные посчитаны |
| Вторая строка `all`, повторная колонка навыка, код, который встречается снова после другого блока | берётся первое, о повторе сказано один раз |
| Чужих кодов на вкладке больше 10 | названы первые 10, остальные посчитаны |
| Блоки весят больше 250 тыс. знаков (десятки проектов со всеми навыками справочника в каждой строке) | доли с планом не сохраняются, названия навыков берутся, сказано |
| Заметок о развесовке больше 50 тыс. знаков | показаны первые, остальные посчитаны |
| Число не в записи таблицы («0_1», «١») | не доля |

## Развесовка замысла — правила 1.1, 05.10.2026

После чтения развесовки модуль знал навыки проекта, но не знал, как они делятся между заданиями, которые придумал замысел. Теперь замысел называет, какие навыки отрабатывает каждое задание, код считает доли и проверяет суждение, а результат — блок в раскладке вкладки паспорта — показан на странице, лежит в файле «Скачать текст» и скачивается отдельным файлом для паспорта. Первый прогон на модели сделан 05.10.2026 — результаты и сделанное по ним ниже.

**Кто что решает.** Какое задание про какой навык — суждение: его выносит модель замысла, вес от 1 до 5 на пару «задание — навык» (1 — касается, 3 — отрабатывает наравне с другим, 5 — задание в основном про него). Доли — арифметика: её делает код. Модель долей не пишет вовсе: сумму до единицы она не держит, каждая несошедшаяся сумма — повторный платный вызов, а при весах несходящуюся раскладку нельзя выразить.

Калькулятор-инструмент для модели здесь ничего бы не дал: нормировщик — тот же расчёт кодом, только посреди ответа и с шагом переписывания; проверяльщик суммы — тот же повторный вызов. Инструмент нужен, когда его результат меняет следующее решение модели (так с часами: от остатка зависит, убрать задание или сократить). Увидит модель 0,34 или 0,33 — её решение о задании не меняется.

**Почему шкала 1–5.** Проверено на 101 колонке настоящих долей по заданиям из обеих вкладок «Батона»: для каждой перебором найдены лучшие возможные веса — потолок того, что шкала может выразить.

| Шкала | Колонок, где все доли в пределах 0,05 от настоящих | Худшее расхождение |
|---|---|---|
| 1–3 | 73 из 101 | 0,30 |
| 1–5 | 93 из 101 | 0,19 |
| 1–10 | 100 из 101 | 0,07 |

Git в `D1P1_Terminal` — 0,65 у одного задания и по 0,05 у трёх; при весах 1–3 больше 0,43 выразить нельзя. Шкала 1–10 точнее, но это уже доли в десятых: возвращается ложная точность, и вес нечем проверить.

**Вес × часы.** Вес говорит, насколько задание про навык; насколько задание велико, известно из его часов. Навык делится между заданиями пропорционально «вес × часы»: часовое задание целиком про Git не перевешивает восьмичасовое, которое про Git наполовину. Объём модель в весе не учитывает — так сказано в её правилах.

**Что считает код** (`concept/skills.py`).

| Функция | Что делает |
|---|---|
| `planned(request)` | навыки готовящегося проекта: названия из поля «Навыки» и доли из блока проекта на вкладке развесовки. Доли УП берутся, только если в форме тот же набор навыков, что в блоке: доля — часть целого, а с другим набором целое другое |
| `divide(concept, project)` | раскладка: основные задания «01»…, бонусные «Bonus 01»…; по каждому навыку доли заданий из «вес × часы». Название не из проекта и второй вес одного навыка не считаются и возвращаются, чтобы о них сказать |
| `exact(parts)` | части целого → доли в сотых, в сумме ровно 1: каждая округляется вниз, оставшиеся сотые получают потерявшие больше, из равных — стоящий раньше. 1 : 1 : 1 → 0,34 / 0,33 / 0,33 |
| `spread(project, tasks)` | часть проекта (основная или бонусная): доли навыков в проекте — из УП как есть, иначе из суммы весов; каждый навык делится между заданиями |
| `table(block)` | блок строками вкладки: `all`, задания, `check`, `Bonus all`, бонусные задания, `check` |
| `sheet(block)` | те же строки файлом для таблицы: «;» между ячейками, запятая в числах; ячейка, похожая на формулу, пишется текстом |

Раскладка замысла — тот же `SkillBlock`, что и блок, прочитанный из паспорта: `parse_blocks(table(block))` возвращает тот же блок. Она сохраняется с запуском (`Run.skill_block`).

**Что получают модели.** Замысел и проверка — `computed_state.project_skills`: названия навыков, как их сравнивает код (`names`), доли основной части из УП (`main`), а если форма разрешает бонус и УП его называет — навыки бонусной части (`bonus`). Правило замысла (`prompts/designer.md`, шаг 3): только названия из `names`, вес — про само задание, каждый навык основной части — хотя бы в одном основном задании, нет уместного действия — не приписывать, а задать вопрос. ### После прогона — 05.10.2026

Три добавления по итогам прогона; правила для моделей и `PROMPT_VERSION` не менялись — меняется только то, что считает и показывает код.

**1. Два замечания о весах** (`planning.check_task_skills`; `skills.divide` возвращает `peak` и `weighed`). Блок может сойтись по суммам и описывать другой проект, чем план.

- *Расхождение с планом.* У плана есть доли — мерило план: часть работы основных заданий, которую по «вес × часы» занимает навык, сравнивается с долей из строки `all`. Расхождение от 10 пунктов называется: «Problem solving — 36% при 20% в УП».
- *«Только касаются».* Наибольший вес навыка среди основных заданий ниже 3. Без долей УП — о любом навыке проекта; с долями — только о навыке, которому план отводит 0,3 проекта и больше (`NOTABLE`).

Обе границы найдены не с первого раза — их нашли две независимые проверки:

| Версия | Что было | Чем плохо |

| 1 | оба замечания о любом навыке; сравнение дробей `abs(a − b) >= 0.1` | для навыка с малой долей замечания несовместимы: вес 3 снимает «только касаются» и выводит навык за план + 10 пунктов (для одного задания и доли до 0,25 чистых весов нет вовсе). Сравнение решал шум чисел: 30% при 20% молчало, 70% при 80% в том же замысле называлось — не срабатывали 56 из 91 пары целых процентов с разницей ровно 10 |

**2. Бонус из паспорта.** Причина замечания «в УП есть бонусная часть, а бонусных заданий нет» в каждом запуске прогона — форма открывалась без бонуса, хотя план его ждёт. Моделям признак не уходит: запросы к моделям побайтно прежние (сверено проверяющим агентом на четырёх проектах паспорта, с бонусом и без, правила 1.0 и 1.1). Что делает код вокруг модели:

Признак-наличие — цитата нужна для 1 и 2; признак-отсутствие и признак «каждый, все» — для 0 и 1 (цитата нарушения). Оценка без обязательной цитаты или с цитатой не из проекта в итог не входит.
- **Недоверенный текст.** Тег блока запроса, написанный в проекте, перестаёт быть тегом; названия из проекта в сведениях кода обрезаются и не могут продолжиться фразой кода.
- **Сведения кода** говорят только то, что код знает точно (сопоставление «по порядку» не называет «лишний» вопрос; ссылкой не считается имя файла, которое Word превратил в «http://materials/…»).
- **Проверка судьи.** Порядок версий одной серии с точной вероятностью того же результата у судьи, не различающего версии (для 9 пар: 8 и больше — 3,2 %, все 9 — 0,46 %); подсаженные дефекты — упала ли оценка нужного признака; просьба «поставь всем 2» в тексте проекта.

**Квесты и критерии вне итога — 06.10.2026.**

Читатель (`benchmark/repository.py`) не находил ни одного задания в проекте, написанном в стиле бассейна: заголовка «Quest N» он не знал. Такой проект нельзя было ни измерить слоем кода, ни показать судье с верными сведениями — ни шаблон школы, ни README генератора в стиле «квест». Теперь:

- «Quest 3. Recursive», «Bonus Quest 5. Func», «Квест 2: Ветки» — задания; вопросы чек-листа «Quest 3. …» и «Quests 1—2» сопоставляются с ними по номеру;
- строка «Получен Quest N. …» делит квест на сюжет, формулировку и остальное (`Task.quest`: `story`, `statement`, `rest`). В документе Word это заголовок четвёртого уровня, формулировка из нескольких абзацев — несколько таких заголовков подряд; в README генератора — жирная фраза в начале абзаца. Строка внутри блока кода или не в начале строки формулировкой не считается;
- квест группового проекта без номера («Quest: Level 1. Hall») — задание, если под заголовком есть строка «Получен Quest.»; тот же заголовок без неё — заголовок группы квестов. Номера у такого квеста нет, и вопрос «Quest 1» к нему не относится;
- «List N» — раздел теории; строка «Сдать: …» после формулировки — что сдаётся.

Слой кода (`code_layer.py`) читает квест так: «что делать» — формулировка, «что должно получиться» — список сразу после неё (так пишет шаблон генератора), «что сдать» — строка «Сдать:». Квест без этой строки (так пишет бассейн: файл назван в самой формулировке) перечисляется среди заданий, где формат сдачи кодом не прочитан; блокером это не считается. README генератора в стиле «квест», собранный в архив и прочитанный обратно, получает те же замечания проверок текста, что и его черновик.

Четыре шаблона бассейна из папки «Эталоны» после правки читаются: 10 квестов (3 бонусных), 7, 5 (1 бонусный) и 2 квеста группового проекта, у каждого есть формулировка; «листков» теории — 5, 4, 3 и 1. До правки — ни одного задания.

## Контент в том же чате — версия 0.3 генератора

После согласования замысла в чате появляется чипс «Подготовить контент». Порядок задал методолог: README собирается последним, до этого весь материал читается как текст.

`что получил генератор → название и аннотация → задание с пояснением → его материалы → … следующее задание … → теория и введение → весь текст целиком → критики → перенос в README кодом`

1. **Что получил генератор** (`content/handoff.py`, карточка считается кодом). Задания и часы, ОР, требования заказчика, ОР программы, аудитория, инструменты, сторителлинг, место в УП, приложенные файлы (сколько знаков передано из скольких), обоснования замысла, открытые вопросы, незакрытые замечания проверяющего, правила методистов. Пропуск виден до того, как по нему написан текст. Какие поля замысла не передаются и почему — список в `tests/test_bridge.py`: новое поле в замысле роняет тест, пока кто-то не решит, нужно ли оно генератору. Файлы с ролью «Для проверяющего» (могут содержать ответы) получает только критик.
2. **Название и аннотация** — один вызов. Обещание проекта: что участник сделает и что получит.
3. **Задания и их материалы** — строго по одному: задание → согласование → материалы к нему (файлы, которые впервые нужны в этом задании) → согласование → следующее задание. Проверять файл удобнее рядом с заданием, пока оно перед глазами. Новых файлов на задание — не больше двух: модель обычно добавляет лишнее — справки по Figma, Miro, образцы Markdown, которые повторяют теорию; такие код не добавляет и пишет об этом в чате, нужный файл методолог просит сам. Согласованное задание 1 — образец для остальных; следующее пишется, когда предыдущие согласованы, и видит их. К каждому модель пишет пояснение для методолога: какой пункт замысла и какие ОР реализует, почему сдача это доказывает, что участник решает сам, как проверит пир, связь с другими заданиями, допущения. Пояснение пишет та же модель, поэтому оно объясняет задание, но не доказывает его: сверять нужно задание с замыслом. В README пояснение не попадает. Задание называет, что участнику нужно понять (из этого строится теория), и нужные ему файлы.
4. **Теория и введение** — после всех заданий, в фоне подряд.
   - **Теоретический блок** (Глава 2): 2–5 разделов «2.N» по потребностям заданий. Каждый раздел короткий: 2–4 предложения — определение и зачем оно в задании, без решения; вопрос к практике; ключевые слова. Темы про оформление сдачи (Markdown, форматы файлов) не пишутся: это не предмет проекта.
   - **Ссылки — агент из трёх шагов** (`content/research.py`, `core/web.py`). Поиск (Perplexity) отвечает свободным текстом; ссылки код берёт из цитат провайдера в любом формате шлюза и из адресов в тексте. Код открывает каждую: 404, ошибка и не-документ отбрасываются; страница за защитой от роботов (401/403/429) остаётся с пометкой «текст не прочитан». Модель-автор читает заголовки и начало живых страниц и выбирает 1–3 на раздел по номеру кандидата; номер вне списка отбрасывается, адрес модель не пишет. Если ссылок нет или их мало, рядом с кнопкой — «Найти ссылки для теории»; то же по просьбе в чате — найденное приходит правками «было → стало». В журнал сервера пишется строка `search model=… citations=… text_links=…` — видно, где шлюз отдал ссылки.
   - **Введение, инструкция, заключение**: введение с ситуацией проекта, пункты инструкции проекта (допускается / запрещено / обязательно) к постоянным пунктам школы, заключение без анонса следующего проекта.
   - Материалы, добавленные позже из чата, пишутся здесь же. Каждый файл видит уже написанные, чтобы персонажи и данные совпадали.
   - **Чек-лист проверки** — после согласования теории и материалов, сразу за всем текстом: карточка с дисклеймером, вопросами (пункты для пира из заданий) и стандартными вступлением и правилами школы, ссылка «Открыть файл» (`GET …/check-list-preview`). Тексты хранятся в черновике (`checklist`): при создании копируются из `school.yaml`, дальше правятся в чате правками «было → стало» (часть «Чек-лист»: дисклеймер, вступление, правила). Дисклеймер пишет методолог — «Дисклеймер чек-листа: …» — модель переносит его дословно, сама не сочиняет; в `check-list.yml` он становится последним пунктом `guidelines`. Пока его нет, а правила программы его требуют, это видно в проверках. Критик чек-лист не проверяет.
5. **Весь текст целиком** (`GET …/text`) — после согласования теории и материалов: в порядке чтения, с пояснениями к заданиям и служебными полями материалов. Участник этого текста не получает.
6. **Критики** — без баллов, их замечания — советы. Методический критик работает на `PROJECT_LAB_REVIEWER_MODEL`, если она задана, чтобы текст не проверяла модель-автор; он сверяет текст с замыслом, а не с пояснениями: P2P, сила действия под ОР, проверка пиром на чужом компьютере, уровень, связность задания, материала, теории и сюжета. Фактический критик — тот же агент: поиск свободным текстом, код открывает страницы, модель-автор оформляет пункты и ссылается только на открывшиеся страницы; вердикт без источника становится советом. «Учесть» у замечания отправляет его в чат, ассистент превращает его в правку. Если текст менялся после проверки, чат это отмечает, проверку можно повторить.
7. **README и чек-лист** — только код, по исходному шаблону генератора (`src/content_factory/didactics/readme_template.md`): название и аннотация, `## Содержание` (списком, с якорями GitLab), `## Глава 1. Введение и инструкция` (`### Введение`, `### Инструкция`), `## Глава 2. Теоретический блок` (`### 2.N` — текст, «Где изучить», «Вопрос к практике»), `## Глава 3. Практический блок` (`### Задание N. …` с блоками «Что нужно сделать», «Что должно получиться», «Ограничения и условия», «Формат сдачи», «Переход к следующему заданию»; бонус — «Бонусное задание N*: …»), `## Заключение`. Задания ссылаются на свои разделы теории. Шаблоны — `templates/README.md.j2`, `templates/check-list.yml.j2`; заголовки и постоянные блоки школы — `templates/school.yaml` («Как учиться в «Школе 21»» — первый подраздел Главы 1, как в PM1; в шаблоне генератора его нет, флаг `how_to_learn_in_readme`).

**Правки** на любом этапе: сообщение становится карточкой «было → стало» по части (название, задание, тема теории, введение, материал). Применить, изменить руками, отклонить, отменить; устаревшая правка не применяется. «Пойдёт» применяет последние правки или согласует обсуждаемую часть, «дальше» выполняет шаг с кнопки. Согласованное модель не переписывает.

**Проверки кодом** (`content/checks.py`). Блокируют перенос в README: ответ или служебная пометка в материалах, заданиях или теории; задание без «Что нужно сделать», «Что должно получиться», формата сдачи или пунктов для пира; неполный черновик — не всё согласовано, правки без решения, заглушки, материал не читается как свой формат, критики не запускались. Предупреждают: ОР без основного задания, часы не сходятся, задание без темы в теории, тема без ссылок, ссылка не из поиска, повтор текста между заданиями, в правилах программы есть дисклеймер, а в чек-листе его нет.

**Вызовы модели**: 1 (название) + число заданий + 1 (теория) + 1 поиск + 1 (выбор ссылок) + 1 (введение) + число материалов + 1 критик + 1 поиск + 1 (оформление фактов). На 5 заданий и 3 материала — 16, плюс правки из чата. Страницы код открывает сам, без модели.

Черновики — `data/content/{run_id}.json` (`PROJECT_LAB_CONTENT_DIR`), доступны только владельцу; черновик прошлой версии генератора откладывается в `.bak`, а не подгоняется под новую схему.

Промпты: `content/prompts/` — system (общие правила P2P), style (с 0.5), summary, task, theory_plan, primary и excerpt (с 0.6), theory, sources (поиск ссылок), links (выбор среди открывшихся страниц), frame, material, critic, facts (поиск), facts_select, revise. **Вход.** В форме два поля: «Стиль подачи» (`Brief.style_profile`: пусто — предложит ассистент, `quest`, `legend`) и «Сквозной сюжет серии» (`Brief.series_story`, свободный текст до 6000 знаков). Замысел их не читает: они не входят в свидетельства, в отпечаток формы, в запросы моделей замысла и в сравнение версий (`Brief.for_concept()`, `concept/models.PRESENTATION`), и их смена не требует новой версии замысла. **Шаг «Стиль»** — первый на маршруте, до любого текста: `стиль → название и аннотация → задания …`. Один вызов (`prompts/style.md`, ответ `StyleDraft`): стиль, обоснование с фактами замысла и ценой другого стиля, сюжет проекта в 3–8 предложений и до четырёх вопросов, без ответа на которые сюжет пришлось бы выдумывать. Стиль, названный методологом, код оставляет, что бы ни ответила модель; если ассистент видит в нём риск, он называет его в обосновании. Дальше:

- ответы на вопросы методолог пишет в чате — модель чата вписывает их в сюжет и убирает отвеченные вопросы правками «было → стало»;
- стиль меняется чипсом («Сменить стиль на …» — сюжет пишется заново) или словами (правка поля «Стиль подачи»);
- «да» под открытыми вопросами о сюжете код не считает ни согласием, ни ответом и переспрашивает; если последний вопрос задал ассистент в чате, «да» уходит модели как ответ на него;
- согласованный стиль чипсом не меняется.

Стиль хранится в черновике (`ContentDraft.style`: `profile`, `reason`, `story`, `questions`, `status`, `chosen_by`, `written_for`). Он входит в то, что читают автор названия, заданий, теории, введения, материалов, критик и модель чата: в системный промпт добавляется описание стиля (`content/styles/quest.md` или `legend.md`), в данные — `project.style` с сюжетом.

**Что меняется в задании.** К прежним полям добавлены `examples` (строки «ввод → вывод», `⏎` — перенос строки внутри стороны; код оставляет только строки со стрелкой и называет отброшенные) и `check` (как задание проверят). Поля одни для обоих стилей, названия и вид в README — по стилю:

| Поле | Квест | Рабочая легенда |
|---|---|---|
| `context` | сцена перед квестом | что создаёшь и с чем работаешь |
| `steps` | формулировка после «Получен Quest N.» — одним абзацем | шаги списком |
| `expected` | требования к результату | «Должно получиться» |
| `examples` | таблица «Входные данные / Выходные данные» | таблица «Ввод / Вывод» |
| `constraints` | «Внимание» | «Условия» |
| `result` | «Сдать» | «Результат» |
| `check` | — | «Проверка» и колонка «Как проверяется» в таблице «Что сдаётся» |

Стороны примеров выводятся как код: `2*x+3*x`, `<N>` и несколько пробелов подряд читаются буква в букву.

**README** собирает код в одной из трёх раскладок (`templates/README.quest.md.j2`, `README.legend.md.j2`, прежняя `README.md.j2`; слова раскладок — `school.yaml`, раздел `styles`):

- квест: `## Введение` → `## Chapter I` (сцена) → `## Chapter II` (теория «листками» `### List N.`) → `## Chapter III` (`### Quest N.` / `### Bonus Quest N.`, между квестами `***LOADING…***`) → `## Chapter IV` (заключение);
- рабочая легенда: легенда до содержания → `## Старт работы` (правила и таблица «Что нужно → Где найти» по материалам) → `## Теория` → `## Задание N.` / `## Задание N (дополнительное).` → `## Итог` → `## Что сдаётся`.

Чек-лист и «весь текст» называют задания так же, как README.

**Смена стиля после того, как текст написан.** Код помнит, для какого стиля написан сюжет (`Style.written_for`) и в каком стиле написано задание (`TaskContent.written_in` — стиль на момент вызова модели). Расхождение видно на карточках и в проверках кодом как совет, не как запрет. Пометку снимает правка: если в чате переписаны сюжет или ситуация и шаги задания, код добавляет к предложению правку «Для какого стиля написан сюжет» / «В каком стиле написано» — она применяется и отменяется вместе с текстом. Если одна реплика меняет и стиль, и сюжет («давай квест, и сюжет такой: …»), сюжет считается написанным для нового стиля. Методолог может сказать, что часть подходит и так, — тогда модель чата предлагает одну эту правку. Задание, написанное в другом стиле, не даётся следующему заданию как образец. Если вызов при смене стиля не удался, профиль остаётся выбранным, а маршрут предлагает три пути: написать сюжет заново, оставить как есть или вернуть прежний стиль.

**Проверки кодом** (`checks.style_form`, все — предупреждения): у задания меньше двух или больше четырёх пунктов для пира; в рабочей легенде у задания нет «Проверки»; сюжет или задание написаны для другого стиля. Перенос в README блокирует только несогласованный стиль.

**Правила текста** (`prompts/system.md`, `task.md`, `critic.md`): сдаётся результат работы, а не отчёт о ней; чек-лист не вводит требований, которых участник не видел в задании; пунктов для пира 2–4, хотя бы один — действие при проверяющем; если в задании есть примеры или данные, один пункт берёт значение, которого в примерах нет.

**Проекты, начатые до 0.5.** Версия генератора записана в черновике, промпты заморожены при старте. Такой черновик идёт прежним маршрутом, без стиля и новых полей: модель получает прежнюю схему ответа (`PlainTaskDraft`), README собирается прежним шаблоном. Проверено сравнением с кодом до изменений: 273 запроса к провайдеру из 37 черновиков на разных шагах маршрута совпали с прежними до байта; отпечатки схем ответов, README, всего текста, чек-листа и отпечаток для критиков закреплены в `tests/content/test_style.py`. После пересохранения новым кодом файл такого черновика получает пустые новые поля; прежний выпуск такой файл не прочтёт — откат требует резервной копии данных (`deploy/README.md`).

**Проверка работы.** Тесты: `tests/content/test_style.py`, `tests/concept/test_presentation.py`, `tests/js/content.test.mjs`. Независимый проверяющий (отдельный агент, копия кода, свои скрипты) прошёл дважды: первый проход — один блокер (схема ответа у старых черновиков получила новые поля; подставная модель тестов этого не видит, потому что схему к запросу добавляет клиент модели), четыре серьёзных и двенадцать мелких замечаний; второй — одно серьёзное (пометку «написано в другом стиле» нельзя было снять) и девять мелких. Исправлено всё, кроме перечисленного ниже.

Мутационный прогон изменённых функций — 56 функций, 1948 мутантов: убито 1831 (94 %). Прогон показал три пропуска и все три закрыты: (1) если одна реплика меняла и стиль, и сюжет, карточка всё равно помечала сюжет как написанный для прежнего стиля — исправлено в `edits.rewritten`; (2) маршрут черновика, начатого до стилей, был закреплён сравнением запросов, но не тестом по шагам — тест добавлен; (3) оглавления README обеих раскладок, правила вывода строки как кода и то, что модель чата и модель стиля получают сюжет, не были закреплены тестами — добавлены. Оставшиеся 117 выживших — запасные значения словарей при существующих ключах, формулировки сообщений и ветки, существовавшие до этой работы (материалы, ссылки, отказ в согласовании). ## Подача теории, выдержка из первоисточника, места картинок — генератор 0.6, 06.10.2026

Решения методолога 6, 7 и 8 от 06.10.2026.

**Шаг «Подача теории»** стоит после заданий и перед теорией: `… задания → как подать теорию → теория, введение, инструкция → …`. Один вызов (`prompts/theory_plan.md`, ответ `TheoryPlanDraft`): вариант подачи, есть ли у участников интернет, нужна ли выдержка из первоисточника на английском, обоснование с фактами замысла, короткий пример одного раздела на материале проекта и до трёх вопросов. Хранится в `ContentDraft.theory_plan`.

| Вариант (`presentation`) | В README | В материалах |
|---|---|---|
| `chapter` — короткая глава (по умолчанию) | раздел в 2–4 предложения, ссылки, вопрос к практике | — |
| `notes` — конспект в README | конспект раздела: 5–12 предложений, по которым можно работать без поиска | — |
| `materials` — конспект в материалах | таблица «что изучить → где найти» | файл `materials/theory.md` с конспектами |
| `both` — коротко и конспект | короткая глава и строка «Подробнее — в материалах» у каждого раздела | тот же файл |

- Вариант меняется чипсом («Выбрать: …») без вызова модели; обоснование и пример на карточке тогда помечены как написанные для другого варианта (`TheoryPlan.written_for`), пример для выбранного пишется по чипсу «Показать пример для этого варианта». Словами меняются вариант, интернет, выдержка и список вопросов — правками «было → стало» части «Подача теории».
- Что задал методолог, код сохраняет: выбранный вариант, а при выбранном варианте — ещё и ответы про интернет и выдержку. Если план изменили, пока модель писала предложение, остаётся план методолога.
- «Да» под открытыми вопросами плана код не считает ни согласием, ни ответом и переспрашивает (`api.plan_asked`).
- Согласованный план чипсом не меняется; словами — меняется, и проверки говорят, чего после этого не хватает.

**Что пишется по плану.** При `notes`, `materials` и `both` автор теории получает схему `NotedTheoryDraft`: у раздела, кроме короткого текста, есть конспект (`notes`). При `chapter` схема прежняя (`TheoryDraft`). Если интернета нет, ссылки не ищутся и не показываются, предупреждение «у темы нет ссылок» не выводится, поиск ссылок из чата не запускается.

**Файл конспектов** `materials/theory.md` собирает код из согласованных разделов (`render.theory_file`, шаблон `templates/theory.md.j2`): конспект, ссылки, выдержка, вопрос к практике. Он входит в архив, ссылки README ведут на якоря его разделов. Если такое имя занято материалом задания, берётся первое свободное: `theory_notes.md`, `theory_notes_2.md`.

**Выдержка из первоисточника на английском** (`research.find_excerpt`, промпты `primary.md` и `excerpt.md`). Модель английский текст не пишет:

1. поисковая модель называет страницы первоисточников; страницы, названные в ответе, открываются первыми;
2. код открывает до шести страниц и читает до 20 000 знаков каждой; остаются страницы с английским текстом (латиница и частые английские слова);
3. модель-автор выбирает страницу и отмечает в её тексте выдержку;
4. код берёт выдержку, только если она стоит на странице дословно, начинается и кончается как предложение, не вырезана из середины слова, длиной от 40 до 400 знаков и написана по-английски. Иначе в чате сказано, почему она не взята.

Выдержка хранится в `Theory.excerpt` со ссылкой на страницу и выводится цитатой; знаки Markdown в ней экранируются, чтобы читатель видел текст страницы буква в букву. В чате её можно убрать и вернуть, но не переписать — ни правкой модели, ни через «Изменить». Найти другую — чипс «Найти выдержку из первоисточника» или слова «найди выдержку из первоисточника».

Ограничение: из ячейки берётся текст. Если адрес записан гиперссылкой с другой подписью, прочитается подпись — книга открывается в режиме чтения, где цели гиперссылок недоступны. Карточка такое значение пометит.

**Файлы проекта называются путём от корня репозитория** — `materials/team.csv`, `src/report.md`. Правило стоит в общем промпте авторов (`content/prompts/system.md`) и проверяется кодом (`checks.paths`, предупреждения):

- в тексте записан адрес репозитория этого проекта — по вебу или по ssh, с `.git`, со страницей файла; сосед с похожим именем (`…ID_157` и `…ID_1578`) не считается;
- файл назван адресом в GitLab (`…/-/blob/…`), когда адрес проекта неизвестен;
- ссылка ведёт на путь одного компьютера (`C:\…`, `file://`, `~/…`, `/home/…`); путь, который просто начинается с `/`, — путь от корня репозитория, он не трогается;
- ссылка ведёт в `materials/` на файл, которого в проекте нет.

Адрес ищется во всех текстах проекта, включая код и материалы-данные; ссылки читаются там, где текст показывается как Markdown (аннотация, введение, задания, теория, материалы `.md` и `.txt`), и не читаются внутри кода. Ссылки, которые README собирает сам, всегда были путями от корня.

Правило и проверка действуют для черновиков, начатых версией 0.7 (`ContentDraft.since`). Черновики 0.6 и раньше идут как шли: 80 сохранённых черновиков (37 до стилей, 43 версии 0.6), продолженных со всех шагов маршрута, дали те же 643 запроса к моделям буква в букву; в сохранённом файле добавилось одно пустое поле `handoff.repository`.

**Страница проекта в отдельной вкладке** (`static/document.js`) читает Markdown сама. Теперь она показывает:

- таблицы — с выравниванием колонок, `\|` внутри ячейки, строками до пустой строки; таблица может стоять сразу под строкой текста;
- цитаты, в том числе вложенные и с таблицей или списком внутри;
- нумерованный список с того номера, который написан: после блока кода, таблицы или цитаты шаги не начинаются с единицы; блок кода с отступом под шагом — часть шага; списки в три уровня; флажки `- [ ]`;
- код между несколькими обратными кавычками (`` `` echo `date` `` ``); звёздочки и подчёркивания вокруг пробелов и внутри слов — как текст;
- ссылки: на файл проекта — открывает его на этой же странице (`document?run=…&doc=file&path=…`, сервер отдаёт файл через `GET /api/content/{id}/file?path=`), адрес в угловых скобках (так шаблон пишет источник выдержки), скобки внутри адреса, адрес, записанный без разметки;
- якоря заголовков по тому же правилу, что `render.anchor`: подчёркивание сохраняется (`#quest-3-ft_strlen`).

Страницы модуля (`/`, `/document`, `/classic`) отдаются с `Cache-Control: no-cache`. До 07.10.2026 этого заголовка не было, и браузер после обновления продолжал показывать сохранённую страницу со старым скриптом — срок он выбирал сам, тем дольше, чем старше файл (страницу документа от 30.09 — около 16 часов). Всё вставляется как текст, не как HTML; ссылки с другой схемой (`javascript:`, `data:`) ведут в никуда. Повторения во всех выражениях ограничены: текст из одного повторённого знака страницу не подвешивает.

## Три названия на выбор — генератор 0.9, 07.10.2026

Замечание методолога: «название проектов всегда короткое и неинтересное». Причина была в наших же текстах, а не в модели: промпт названия просил «лаконичное название из 1–3 слов, отражающее суть проекта» и разрешал «опереться на название из замысла» (а оно приходит из строки учебного плана); стиль «квест» говорил «1–3 слова о теме проекта». Длина взята из паспорта проекта школы (признак P01), тема — наша формулировка. В эталонах тему в заголовок не выносят: интенсив называет проект образом из сюжета («Тишина», «Битая память»), бассейн SQL ставит в README фразу-вызов при сухом имени репозитория.

Схема принимает от одного до шести названий — шаг маршрута не должен падать из-за счёта; код берёт первые три разных (`flow.titles`), сняв кавычки вокруг и точку в конце (`flow.bare`).

Своё название или «возьми второй» — словами: чат видит варианты в `parts` и предлагает обычную правку `summary · title`. После согласования кнопок нет, сохранённая кнопка отклоняется.

## Часы проекта: число заданий, объём задания, проект больше нормы — генератор 0.10, 29.10.2026

Замечание методолога 28.10: «6 и 60 часов при генерации ничем не отличаются». Причин было три, и все — в нашем коде и текстах, а не в модели.

| Что | Было | Стало |
|---|---|---|
| Число заданий без заданного методологом | `tasks_typical: 5` в `concept/config/workload.json`: 6, 12 и 24 ч — по 5 заданий | часы ÷ 3,5 ч (середина нормы 1–6 ч), с округлением вверх от половины (`workload.budget`): 6 ч — 2, 12 ч — 3, 24 ч — 7, 48 и больше — 8 |
| Объём задания | автору задания передавались его часы, но промпт о них молчал и велел держаться объёма первого задания | промпт задания меряет работу часами — четыре полосы: до 2 ч, 2–4, 4–6, больше 6 (`prompts/task.md`); первое задание — образец стиля, не объёма; автор видит часы остальных заданий; объём данных материала — по часам его заданий (`prompts/material.md`); критик проверяет соответствие (`prompts/critic.md`, пункт 13); в пояснении методологу — фраза, почему объём соответствует часам |
| Проект больше, чем помещается в норму (8 заданий × 6 ч = 48 ч) | строка среди замечаний бюджета; замысел делал обычные 8 заданий, каждое длиннее нормы | маршрут останавливается на входах и спрашивает: уменьшить часы, разделить проект или оставить часы с длинными заданиями (`workload.overflow`, `route.next_step` — шаг `keep_hours`) |

**Как устроен вопрос о часах.** Ёмкость проекта — `main_tasks_max × task_hours.max` из норм. Если часы её превышают, на шаге «Входы разобраны» вместо «Подготовить замысел» — вопрос с вариантами и кнопка «Оставить N ч — задания длиннее нормы». Меньше часов — словами в чате («трудоёмкость 48 часов»): это обычная правка поля и новая версия. Решение хранится в запуске (`Run.hours_kept`, схема хранения 5): у каждой версии свои часы, и вопрос задаётся заново для каждой. Обойти вопрос нельзя ни одним путём: «дальше» в чате повторяет вопрос; «Применить правки и продолжить» останавливается на нём; новая версия, запущенная с просьбой продолжать сразу, ждёт на входах; `POST /api/runs/{id}/confirm-inputs` без `keep_hours=true` отвечает 409 с тем же текстом — так и классическая страница не проскочит. Оставленные часы видит проектировщик замысла: строка `computed_state.hours_kept`.

**Что не изменилось.** Число, названное методологом, проверяется по-прежнему по диапазону `tasks_min–tasks_max`. Принятые проекты программы «Батон» в диапазон укладываются и ничем не останавливаются. Но без названного числа модуль теперь предлагает им меньше заданий, чем было в программе: 6 ч — 2 вместо 6, 8 ч — 2 вместо 5–6, 15 ч — 4 вместо 5–6. Это прямое следствие решения «часы ÷ 3,5». Вернуть прежнее — одна строка `"tasks_typical": 5` в файле норм; код его поддерживает.

**Старые проекты.** Черновики, начатые до 0.10, пишутся по своим замороженным промптам и получают те же входные данные: 26 черновиков версии 0.9 на каждом шаге маршрута отправляют те же 232 запроса до буквы, документы и проверки совпадают. Запуски замысла хранят свой бюджет часов: пересчитан он будет только для новых. Запуск, остановленный на входах до этого релиза, спросят о часах так же.

## Как модель в чате держит разговор — тесты и сценарии

Три уровня, от дешёвого к настоящему:

1. **Контекст, который получает модель, и решения кода без неё** — `tests/content/test_chat_context.py`, `tests/concept/test_dialogue.py`. Модель здесь по сценарию, проверяется то, что ей передаётся и что делает код: фокус (что на экране; ответ на ожидающее предложение — про поля этого предложения), окно истории (8 реплик до текущей, без служебных, с тем, что стало с каждым предложением: ждёт, применено, отклонено), номера замечаний критиков, статусы частей. Короткие реплики код разбирает сам: «пойдёт», «дальше», «покажи весь текст»; таблица хитрых реплик («пойдёт, но срок поменяй», «дальше не надо», «весь текст задания 2 сократи») — там же. Новое предложение по тому же полю заменяет старое ожидающее, иначе применение старого вернуло бы прежнюю формулировку.
2. **Мутационный прогон кода чата** — `python -m project_generator_lab.mutation --chat` (intents, правки, API контента, диалог замысла). Первый прогон 30.09.2026: убито 71% мутантов (1286 из 1806), после новых тестов — 74%. Выжившие показали пропуски тестов: фокус на ожидающем предложении не отличался от запасного; «пойдёт» при ожидающей правке в чате контента не проверялся; «дальше» при блокирующих проверках не объяснял, что мешает; повторная правка «не учитывать» перепроверяла уже вырезанный текст и отклоняла бы всё предложение; в чате замысла нумерация пунктов актуальности и окно истории не были закреплены («учти пункт 2» мог указать не туда). На каждый пропуск — тест. Оставшиеся выжившие — в основном формулировки подсказок (`next_step`), это принято.
3. **Сценарии на настоящей модели** — `python -m project_generator_lab.chat_eval` (в Windows `.tmp\lab\chat_eval.cmd`). Короткие разговоры через те же маршруты, что и чат, на копии последнего черновика: точная правка одного поля с сохранением остального текста, «сократи только первый пункт», неясная просьба (нужен вопрос), вопрос без просьбы (без правок), «и там же…» (правка в то же задание), «нет, пусть будет…» (новое предложение заменяет прежнее), просьба добавить ссылку без адреса, просьба положить решение в материалы, дисклеймер дословно, две правки одним сообщением, «кроме задания N», «учти замечание N», и сценарии чата замысла: новый ОР в конец списка, уточнение уточнения, вопрос, ответ на вопрос разбора своими словами (без «Вопрос N:») и два таких ответа одним сообщением — засчитывается, только если ответ записан в задание с номером именно того вопроса, иначе следующая версия спросит снова; реплика строится из открытого вопроса последней версии. Без черновика контента прогон идёт только по сценариям замысла: `--draft` принимает id чата замысла, а по умолчанию, если черновика с теорией нет, берётся последний чат с вопросами разбора. Копия диалога открывается как локальная, поэтому так же проверяется копия боевого диалога (`deploy/eval_answers.sh`); `--out` — папка для отчёта. Итог проверяет код: «да», «поймал код» (модель ошиблась, защита остановила), «нет» (ошибка дошла бы до методолога), «сбой» (модель не ответила). Фоновые задачи и новые версии замысла не запускаются, оригиналы не меняются. Отчёт — `data/chat_eval/<время>/report.md`. `--runs 2` — повтор каждого сценария: модель отвечает по-разному, один прогон — не статистика. Ключи для `--only`: precise, first_step, ambiguous, question, same_place, correction, link, solution, disclaimer, two_edits, show, except_one, finding, outcome, follow_up, concept_question, free_answer, free_answers, explain, joke, method, concept_joke, concept_method.

   Первый прогон 30.09.2026 (gpt-6-sol, черновик «Прототип продукта», 16 сценариев, ~4,5 мин): 14 «да», 2 «нет» — и оба «нет» оказались ошибками сценариев, а не модели. «Две просьбы сразу» просили поменять формат сдачи — модель верно ответила, что это меняет замысел, и спросила, о какой встрече речь (в задании 2 её нет); сценарий заменён на две правки формулировок. «Замечание по номеру»: замечание про задание 3 предлагало дать заготовку, модель поправила материал этого задания — теперь это засчитывается. Сами проверки тоже надо проверять: для этого `tests/test_chat_eval.py`.

## Мутационные тесты

Обычные тесты показывают, что код выполнялся. Мутационные показывают, что тесты заметят, если код изменится: mutmut вносит мелкие правки (`<` → `<=`, `/3` → `/4`, `+` → `-`, строка → `None`) и прогоняет тесты. Если тесты прошли, мутант «выжил»: этого поведения не фиксирует ни один тест.

```bash
pip install "mutmut>=3.8,<4"
python -m project_generator_lab.mutation --min-score 75      # Linux, macOS, WSL; в Windows напрямую не работает
python -m project_generator_lab.mutation --only concept/workload.py --keep   # затем в указанной копии: python -m mutmut show <имя>
```

Мутируются только вычислимые модули: в замысле `workload.py`, `input_semantics.py`, `dialogue.py`, `thread.py`, `patches.py`, `answers.py`, `route.py`, `ingestion.py`, `skills.py`, `benchmark.py`, `freshness.py`, `validation.py`, `planning.py`, `runs.py`; в ядре `llm.py`, `intents.py`, `chat.py`, `contracts.py`, `storage.py`, `web.py`, `isolated.py`, `usage.py`; отчёт о стоимости `usage.py`; в контенте `checks.py`, `edits.py`, `stages.py`, `render.py`, `flow.py`, `api.py`, `store.py`, `models.py`, `handoff.py`, `writer.py`. `--functions` ограничивает прогон функциями (`core.chat.move`, метод — `core.storage.Locks.__call__`). Копия создаётся во временной папке, рабочие файлы и `data/runs` не затрагиваются. Разбор выживших:

- выжившие в логике (`budget`, `check`, `program_position`, `build_patches`) значат, что не хватает теста; на них написан `tests/test_mutation_guards.py`;
- выжившие в тексте рекомендаций и описаниях полей для модели допускаются;
- «эквивалентные» мутанты допускаются: `>` против `>=` при допуске 0,05 в дробных часах поведения не меняет.

Первый прогон: 337 из 791 (43%). После тестов: 602 из 786 (77%). По ходу найдена ошибка: предупреждение «трудоёмкость меньше нормы одного задания» никогда не показывалось, потому что верхняя граница числа заданий принудительно поднималась до 1. Исправлено в `workload.budget`.

Контент (`checks`, `edits`, `stages`, `render`): первый прогон 880 из 1377 (64%), после тестов 1038 из 1389 (75%); после перестройки маршрута 1373 из 1813 (76%). Выжившие в основном в текстах подсказок `next_step`. По ходу найдена ошибка: сохранение черновика обрезало пробелы в материалах, и YAML с отступом в первой строке ломался. Исправлено: содержимое файлов хранится как есть.

**Прогон 05.10.2026 и «таймауты», которые были выжившими.** Развесовка навыков (`skills.py` и чтение вкладок в `ingestion.py`, включая `parse_curriculum`): убито 1269 из 1330 мутантов (95%). Из 60 выживших 14 закрыты тестом, написанным после прогона (те же поломки повторены вручную — все замечены); остальные — формулировки сообщений и равнозначные замены. Без теста остались три мелочи: номер колонки в имени повторного заголовка, начальное значение целей блока, счёт пустых строк в самом начале вкладки. Первый заход шёл в пять раз медленнее обычного, а процессы-исполнители не занимали процессор. Стек зависшего процесса (`py-spy dump --pid …`) показал: тест ждёт ответа на загрузку файла по HTTP. mutmut проверяет каждого мутанта в процессе, порождённом `fork` от главного; пул потоков разбора файлов (`core/isolated.POOL`) после `fork` помнит свободные потоки, которых в новом процессе нет, и отданная ему работа не начинается. Мутант, которого не убил ни один тест до первого теста с загрузкой, получал состояние «таймаут» — ни убит, ни выжил. После исправления (порождённый процесс получает свой пул, `os.register_at_fork`) все 20 таких мутантов в уже пройденных функциях оказались выжившими. Правило на будущее: состояние «таймаут» в отчёте — не «убит»; если их больше одного-двух, сначала выяснить, чего ждёт процесс.

Что показали выжившие: в тестах все строки справочника были одной длины; в тестовых книгах не было посторонних вкладок между планом и развесовкой (в паспорте их два десятка, и `continue` → `break` в обходе книги не замечал ни один тест); сравнение названий навыков между проектами («ё», опечатка «Analisys», знаки) не держал ни один тест. В `parse_curriculum` то же нашлось в строках прежних версий: формат «Групповой» с заглавной буквы, одно число в размере группы, «Без блока», 201-й проект. На каждое — тест. Убрано лишнее: округление в `said`, аргументы `nearest`, повторявшие значения по умолчанию.
